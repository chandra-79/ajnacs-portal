Every cache is a bet that the expensive computation behind it won't be asked for very often — and the cache stampede is that bet's failure mode: a popular key expires, and in the window before anyone repopulates it, *every* concurrent request for that key misses simultaneously and executes the expensive path in parallel — a thousand identical queries hitting a database sized for one per TTL. The pathology compounds itself: the origin, suddenly overloaded, slows; slow recomputation widens the miss window; more requests pile into the gap (the utilization-curve explosion, self-inflicted); and the system discovers that its cache wasn't an optimization — it was load-bearing capacity, and its expiry semantics were an outage scheduler. The variants share the shape: the *deploy stampede* (cold caches fleet-wide after a restart), the *midnight stampede* (synchronized TTLs from batch-loaded keys expiring together), and the *celebrity-key stampede* (one hot key whose recomputation is expensive — the hot-partition problem's caching cousin).

## The four mechanisms, and what each actually solves

**Request coalescing (single-flight)** — the direct fix: when a key misses, *one* request wins the right to recompute (an atomic lock/claim on the key — the compare-and-swap idiom); everyone else waits briefly for the winner's result or serves stale meanwhile. This converts N simultaneous recomputations into one, which is the entire stampede, solved — per process trivially (the in-process single-flight primitives), across a fleet with a shared claim in the cache tier itself (with the lock-TTL-and-fencing honesty from distributed-locking practice: the winner that dies mid-recompute must not wedge the key — claim expiry sized to recompute time, and the waiting strategy decided: brief block, serve-stale, or fail-fast per the request's tier). The subtlety worth designing: coalescing turns one slow recompute into *everyone's* latency — which is why it pairs with the next mechanism rather than replacing it.

**Stale-while-revalidate** — the availability fix: expiry stops meaning "unavailable" and starts meaning "refresh opportunistically" — the stale value serves instantly while one background refresh (coalesced, per above) updates it. This is the HTTP-caching directive generalized into application caches (soft-TTL/hard-TTL two-tier expiry: within soft, serve fresh; between soft and hard, serve stale and refresh async; past hard, the value is genuinely gone and coalescing carries the load), and it deletes the user-facing cost of the entire mechanism — the staleness budget made explicit and spent deliberately, per every derived-data discipline. For most read-heavy systems this is the single highest-value cache upgrade available: misses stop existing as a user experience.

**Probabilistic early refresh** — the elegant refinement: rather than everyone observing the same expiry instant, each request *near* expiry rolls a die weighted by recompute cost and time-remaining (the XFetch algorithm's insight), so refresh happens *before* expiry, by exactly one lucky request, with no synchronization at all. Beautiful where it fits (uniform request streams over moderately hot keys); less load-bearing than the first two in practice, but worth knowing because it solves the problem with zero coordination — the recurring ideal.

**Jittered TTLs** — the synchronized-expiry fix: TTLs set as base ± random spread, so the ten thousand keys loaded by the 2 AM batch job don't expire as one wave (the variance-injection discipline from retry practice, applied to expiry — synchronized anything is self-inflicted burstiness, per the queueing math). Trivial, universal, and the first thing to check when the graph shows periodic miss-rate spikes at suspiciously round intervals.

**And the deploy/cold-start case** gets its own answer, because none of the above helps an *empty* cache: warmup as a deployment step (the readiness-gate discipline — the instance that declares ready before its hot keys are loaded is volunteering for the stampede; pre-warm from the previous generation's key inventory or a snapshot, per the connection-draining patterns), and fleet-wide restarts staged so the cache tier never goes globally cold (the rolling-deploy logic, applied to cache state).

## Composition and the design review

The mechanisms compose into the standard mature stack: **jittered TTLs everywhere** (free), **soft/hard expiry with stale-while-revalidate on the read path** (the availability floor), **single-flight coalescing on every recompute** (the origin's protection — and note it protects against the cold-key case SWR can't), **probabilistic refresh where streams are smooth**, and **warmup in the deploy pipeline**. The review questions that catch the gaps early: *what happens when this key expires under peak concurrency?* (the answer "everyone recomputes" is the finding), *what's the blast radius of this cache being empty?* (if the answer is "the database dies," the cache is load-bearing capacity and deserves capacity-planning treatment — the origin sized for miss storms it will someday meet, or admission control in front of it per the load-shedding contract), and *which keys are hot enough to deserve the full stack?* (the celebrity keys get coalescing and SWR mandatorily; the long tail can live with jitter alone — the criticality tiering, at key granularity).

The closing frame: stampedes are the canonical example of this series' oldest lesson — the system that works at low concurrency and detonates under load, because a shared assumption (the cache is populated) failed *simultaneously for everyone* rather than gradually for some. The fixes are all variance-and-coordination engineering: desynchronize the expiries, coalesce the recomputes, decouple staleness from unavailability — twenty lines of library code in most stacks, versus the postmortem titled "database overload following cache expiry," which is among the most preventable documents in operations.
