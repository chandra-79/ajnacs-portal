Here is the situation every distributed system eventually faces: a client sends "charge the customer $500," the network hiccups, and no response arrives. Did the charge happen? The client cannot know — and both available moves are wrong. Retry, and maybe charge twice. Don't retry, and maybe the customer got their order for free. This is not an edge case; it's the fundamental condition of communicating over an unreliable network, and it has exactly one systematic exit: **make the operation safe to repeat**, so the client can always retry. That property is idempotency, and it's less a technique than a design discipline that touches APIs, databases, queues, and organizational habits.

## Why "exactly-once delivery" won't save you

The recurring hope is that infrastructure will solve this — a broker or protocol that delivers each message exactly once. The uncomfortable theory result: over an unreliable network, delivery guarantees come in two flavors, **at-most-once** (may lose messages) and **at-least-once** (may duplicate them), and systems that matter choose at-least-once, because losing a payment is worse than seeing it twice. What vendors market as "exactly-once" is, on inspection, at-least-once delivery *plus deduplication* — i.e., idempotency, implemented somewhere, by someone. The only question is whether that someone is you, deliberately, or an accident report. **Exactly-once *processing* is achievable; exactly-once *delivery* is not — and the bridge between them is idempotent handling of duplicates.**

Duplicates don't even require infrastructure failure: users double-click, mobile apps retry on flaky radios, load balancers resend after timeouts, queue consumers crash after processing but before acknowledging (the canonical duplicate generator), and your own retry middleware does exactly what you configured it to do.

## The workhorse: idempotency keys

For APIs performing non-idempotent operations (payments, orders, provisioning — anything where "do it twice" differs from "do it once"), the standard pattern is the **idempotency key**: the *client* generates a unique key per logical operation (a UUID minted when the user hits "pay," not per HTTP attempt — the distinction is the whole point), sends it in a header, and retries with the *same* key. The server, per key: first sight → process, store the result keyed by the idempotency key, return it; repeat sight → return the stored result without re-executing; concurrent sight (the race where attempt two arrives while attempt one is mid-flight) → block or reject with "in progress," which requires the key check to be an atomic reserve (unique-constraint insert), not a read-then-act.

The implementation details that separate working versions from incident generators: the key store needs a **TTL matched to realistic retry horizons** (24 hours is common — long enough for a mobile client that slept through the night, bounded enough to be storable); the stored response must include *failures that shouldn't re-execute* (a definitive card decline should replay as a decline, not re-attempt the charge); and key acceptance should validate the request body hash, so a client bug that reuses a key with different payloads gets an error instead of silently receiving someone else's stored result.

HTTP's method semantics do some of this work for free — GET, PUT, and DELETE are *specified* idempotent (PUT "set state to X" repeats harmlessly; contrast POST "append X") — which is why "can this be a PUT with a client-chosen resource ID?" is the first design question. `PUT /orders/{client-generated-id}` gets you idempotent creation with no header machinery: the second attempt is an overwrite of identical state or a conflict, never a second order.

## The database side: natural idempotency beats bookkeeping

The strongest implementations make the *operation itself* idempotent rather than wrapping bookkeeping around a fragile one. The toolkit: **unique constraints as the enforcement of "at most one"** (one payment row per idempotency key, one account per email — let the database's atomicity be the arbiter, and treat constraint-violation-on-insert as "already done, fetch and return it"); **absolute state over relative mutation** (store `balance_after` events or set `status = 'shipped'`, rather than `UPDATE balance = balance + 500`, which is the textbook non-idempotent operation); **conditional updates as guards** (`UPDATE ... WHERE status = 'pending'` — zero rows affected means someone got there first, which is an answer, not an error); and upserts (`INSERT ... ON CONFLICT DO NOTHING/UPDATE`) for the create-or-update shape. A useful heuristic for reviews: any SQL containing `+=`-style arithmetic or any handler whose effect depends on how many times it runs is a duplicate-sensitivity finding.

## Queues and the outbox: idempotency's other half

Message consumers live under at-least-once redelivery, so **every consumer must tolerate duplicates** — that's not a nice-to-have, it's the contract. The patterns: consumers that apply absolute state are naturally safe; consumers with side effects need **dedup via processed-message IDs** (an `inbox` table with a unique constraint on message ID, checked *in the same transaction* as the business effect — dedup in Redis while the effect commits to Postgres reintroduces the race across two systems); and Kafka-style transactional processing covers the within-Kafka case while external side effects still need their own idempotency.

The producer side has its own classic: the **dual-write problem** — service commits to its database, then crashes before publishing the event (or vice versa), leaving the two systems permanently disagreeing. The standard fix is the **transactional outbox**: write the business change *and* the outgoing event to an `outbox` table in one transaction, with a relay (CDC or poller) publishing from the table afterward. The relay guarantees at-least-once publication — duplicates again, by design — which downstream consumers absorb because they followed the previous paragraph. Notice the shape of the whole system: *nobody* eliminates duplicates; every layer generates them under failure and every layer tolerates them on receipt. That's what a correct distributed system actually looks like.

## Making it organizational

Idempotency fails most often not in the design review but in the gaps between teams — the service that added retries (client team, Tuesday) calling the endpoint that charges twice (platform team, unaware). The countermeasures are cheap and procedural: **retry policy and idempotency guarantees are documented per endpoint** as part of the API contract (if an endpoint isn't safe to retry, its docs must say so, and its client SDK must not); **duplicate-delivery tests belong in the standard suite** — fire every event twice at every consumer in CI and assert single effect, which catches regressions the happy path never will; and chaos-style **retry storms in load testing**, because the concurrent-duplicate race only shows up under contention. Teams that adopt "every handler assumes it will see every message at least twice" as a review norm stop having this class of incident almost entirely — and the payments-shaped ones they stop having are the expensive kind.

The through-line: unreliable networks made "did it happen?" unanswerable, so mature systems stop needing the answer. Design every effect so that *doing it again is safe*, and retries — the only real remedy the network allows — become free. It's one of the rare disciplines in distributed systems where the theory is settled, the patterns are standard, and the entire remaining difficulty is just deciding to apply them everywhere, including the endpoint someone wrote in 2019 that everyone hopes is fine.
