The SolarWinds and Log4Shell incidents changed how the industry thinks about software supply chain risk. Both showed the same vulnerability: organizations had extensive perimeter controls and almost no visibility into what software they were actually running and whether it contained known vulnerabilities.

Software Bill of Materials (SBOM) and supply chain security practices exist to address this. The challenge is that the tooling is maturing, the standards are still evolving, and the gap between "we generate an SBOM" and "we have meaningful supply chain security" is significant.

**SBOM coverage for deployed digests.** If 190 of 200 unique production image digests link to an inventory generated from the deployed artifact, coverage is 95%. Add freshness and provenance checks, and record who owns remediation when a component is flagged.

## What an SBOM actually is

A Software Bill of Materials is a formal, machine-readable list of the components in a piece of software — libraries, frameworks, and their transitive dependencies — with version information and license data. Think of it as the ingredient list for software.

SBOM formats:
- **SPDX** (Software Package Data Exchange) — Linux Foundation standard, widely supported
- **CycloneDX** — OWASP standard, focused on security use cases, strong tooling ecosystem

Most software today ships without a published SBOM. The US Executive Order on Cybersecurity (May 2021) created requirements for software sold to the US federal government; this has accelerated adoption in commercial software as well.

## Generating an SBOM

SBOM generation is now straightforward for most technology stacks:

```bash
## For container images using Syft
syft ubuntu:latest -o cyclonedx-json > sbom.json

## For Node.js projects
npx @cyclonedx/cyclonedx-npm --output-format JSON > sbom.json

## For Python projects
pip-audit --format=cyclonedx-json > sbom.json

## For Java/Maven
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
```

The SBOM should be generated as part of the build pipeline and stored alongside the artifact it describes. If you are releasing version 2.1.4 of your service, the corresponding SBOM should be retrievable for that specific version.

## Vulnerability scanning against the SBOM

A generated SBOM is primarily useful for vulnerability scanning: cross-referencing the component list against known vulnerability databases (NVD, OSV, GHSA).

```bash
## Grype vulnerability scanner against a generated SBOM
grype sbom:sbom.json

## Or directly against an image
grype my-app:latest
```

The important distinction: vulnerability presence is not the same as vulnerability exploitability. A critical CVE in a library is only exploitable if the vulnerable code path is reachable in your application. Grype and similar scanners report presence; determining exploitability requires more analysis. Start by prioritizing CVSS score above 7 and direct dependencies over transitive ones.

Integrate scanning into CI:
```yaml
## GitHub Actions example
- name: Scan for vulnerabilities
  uses: anchore/scan-action@v3
  with:
    image: "${{ steps.build.outputs.image }}"
    fail-build: true
    severity-cutoff: critical
```

## Provenance and build attestation

Knowing what is in your software is different from knowing that your software was built from the code you think it was. Supply chain attacks like the SolarWinds compromise tamper with build artifacts after code review but before deployment.

SLSA (Supply chain Levels for Software Artifacts) is a framework that defines levels of build integrity:

- **Build L1** requires build provenance.
- **Build L2** adds signed provenance generated by a hosted build platform.
- **Build L3** adds requirements for a hardened build platform and tamper resistance. Review the precise controls in [SLSA v1.2](https://slsa.dev/spec/v1.2/build-track-basics).

In practice for most organizations: SLSA Level 2 provides meaningful protection. Build in a controlled CI environment (not developer laptops), sign artifacts cryptographically, and generate provenance attestation that records what source commit was built and by what build process.

Sigstore/Cosign has become the standard toolchain for signing container images and recording provenance:

```bash
## Sign a container image
cosign sign --key cosign.key my-registry/my-app:v1.2.3

## Verify a signed image
cosign verify --key cosign.pub my-registry/my-app:v1.2.3
```

## Dependency management hygiene

SBOMs and scanning are detective controls. The preventive controls that reduce supply chain risk:

**Pin dependencies to specific versions** rather than ranges. `requests==2.31.0` not `requests>=2.20`. Unpinned dependencies allow supply chain attacks via a malicious version being published to a package registry.

**Lock files and dependency checksums** serve related purposes. Keep a supported lockfile such as `package-lock.json`, `poetry.lock` or `Pipfile.lock`. In Go, `go.mod` participates in module selection and `go.sum` records expected module checksums. Without them, `npm install` in CI may resolve to different package versions than what was tested locally.

**Private package mirror with allowlist**: mirror approved packages to an internal registry (JFrog Artifactory, AWS CodeArtifact, GitHub Packages). Builds pull from your mirror only. This blocks dependency confusion attacks and gives you a control point for new package approvals.

**Automated dependency updates**: tools like Dependabot and Renovate automatically open PRs when dependencies release new versions. Keeping dependencies current significantly reduces the window of exposure to known vulnerabilities.

The supply chain security posture that matters: knowing what you're running, knowing whether it has known vulnerabilities, and having a process to respond when new vulnerabilities are disclosed for components you depend on.

## Bind inventory to the artifact you deploy

Generate evidence for the artifact that actually leaves the release pipeline. A manifest describes intended dependencies. An inventory derived from the packaged artifact can observe libraries copied from another build stage and packages inherited from the base image. Those approaches answer different questions. If a build creates different outputs for different architectures, keep the applicable inventory and digest for each output. Preserve the link from the promoted artifact to the inventory, provenance statement, builder identity, and source revision. A registry tag is convenient for people, but a tag and a version string are insufficient to prove that the deployed bytes match the scanned artifact.

Design verification to succeed outside the original CI job. Given just the deployed digest, an authorized responder should be able to identify the source revision and retrieve the applicable inventory. Try this with an older supported release. Verify that evidence remains accessible after a retention period or registry cleanup. If retained artifacts lose their evidence records, the team can be unable to investigate a newly published advisory even though the old release is still in use.

## Measure evidence quality beyond initial coverage

An inventory that lists a dependency without a version or usable identifier creates extra work during response. Inspect a small set of artifacts for component identity, version, dependency relationships, the tool that generated the data, and known gaps. Distinguish a missing component from an incomplete version identifier. A dependency listed under one naming convention may be known under another in an advisory database. Preserve the raw inventory and the matching technique used by the assessment. The [CISA guidance on software component transparency](https://www.cisa.gov/sites/default/files/2024-10/SBOM%20Framing%20Software%20Component%20Transparency%202024.pdf) describes common baseline attributes and how they can map across formats.

Suppose a fictional fleet runs 80 distinct digests. Evidence exists for 78, but six of those inventories cannot be authenticated or associated with the artifact digest. Verified digest coverage is 72 divided by 80, or 90%. If two unverifiable digests represent most running replicas, an inventory count by distinct digest understates the operational exposure. Record both views, together with owners for the gaps. Deduplicate artifact-level response work, then track deployment-level replacement work separately so that teams know where a new release actually needs to reach.

## Distinguish signature verification from provenance evaluation

A trusted signature can establish that an approved identity signed a specific artifact. A provenance attestation can provide statements about the materials, source revision, and build process. Verification needs artifact and identity policy as well as cryptographic validity. Determine which signing identity and issuer you accept and which builder and source location are expected. An attestation with a valid signature from an unapproved identity should not satisfy deployment policy. Preserve the verification result and the policy version. Sigstore documents its [signature verification options](https://docs.sigstore.dev/cosign/verifying/verify/), and [SLSA Build Track Basics](https://slsa.dev/spec/v1.2/build-track-basics) distinguishes the existence of provenance, hosted signed provenance, and hardened build environments.

In an owned test registry, exercise three benign fixtures. Use a known approved artifact with matching evidence, one signed by an unrelated test identity, and one whose evidence belongs to a different digest. Verify the chosen policy accepts only the first. Then simulate the evidence service being unavailable. Decide what happens to routine promotions, automated recovery, and authorized emergency releases in that state. Rehearse how expiry, logging, and cleanup work for an exception so that an emergency process does not become the daily delivery path.

## Triage from finding to replacement

A scanner finding is a lead for investigation. Start with the affected inventory and identify which versions run where. Consider advisory confidence, exploitability in the intended configuration, data sensitivity, and the exposure of the affected workload. When claiming a component is not affected in a particular product, preserve the evidence for that conclusion and when it was reviewed. A vulnerability status can change when a feature is enabled or the deployment moves. CISA publishes [minimum requirements for vulnerability exploitability statements](https://www.cisa.gov/sites/default/files/2023-04/minimum-requirements-for-vex-508c.pdf) as a reference for recording product-specific status and justification.

Release remediation usually has more than one step. Identify a compatible replacement, build and test it, promote the exact verified digest, and prove that it displaced the old version in the relevant environment. A merged version bump does not prove replacement. Record when the issue was identified, when a responsible owner accepted it, and when the last affected production deployment was removed or explicitly excepted. Look for a recurrent delay such as waiting for upstream fixes or rebuilding images whose owners have moved. That evidence helps the team improve the bottleneck in the response process.

Close the exercise by running a harmless advisory simulation on a component you own. Ask a responder to retrieve evidence using the deployed digest, map an affected component to the responsible service, and verify that a staged rollout ends with the expected new digest. If this cannot be done without the person who created the pipeline, the system still has an ownership and discoverability problem even when the inventory files are valid.
