The relational-versus-document argument quietly lost its subject: Postgres (and its peers) absorbed the document model — JSONB with real indexing, a full path-query language, and transactional semantics — which moved the decision from "which database" to **"which columns."** That's a better decision to have, and a subtler one: the hybrid model done well gets relational integrity where structure is stable and document flexibility where it isn't; done lazily, it produces the worst artifact in modern data modeling — the relational database cosplaying as a document store, with neither the constraints of the former nor the ergonomics of the latter, and a `data` column nobody can explain.

## The placement rule: structure by stability and query shape

The honest criteria for what belongs in JSONB versus columns: **query and constraint participation** — anything you filter on routinely, join on, aggregate over, foreign-key to, or enforce invariants against (the unique constraints and check constraints doing the isolation-level toolkit's work) belongs in typed columns, because columns are where the relational engine's whole value proposition lives: statistics for the planner (the estimate-accuracy machinery from query-plan practice sees into columns and mostly guesses at JSONB paths), constraint enforcement, and cheap indexing. **Genuine schema variance** belongs in JSONB — the payload shapes that differ per integration (the webhook bodies from delivery practice, stored raw per the persist-then-process rule), per-tenant custom fields (the multi-tenancy extensibility problem, solved without the EAV anti-pattern or per-tenant DDL), sparse attribute sets (the product catalog where each category carries different specs — the classic legitimate case), and the audit/event payloads whose *shape* is historical fact rather than current contract. The tell for misplacement in each direction: a JSONB path appearing in every WHERE clause is a column wearing a costume (promote it); a table with forty mostly-null typed columns per category is JSONB wearing a schema (demote the variant tail).

The hybrid idiom that captures most healthy designs: **stable spine, flexible limbs** — identity, relationships, money, status, and timestamps as columns with full constraint treatment; the variant descriptive payload as one JSONB column beside them. And the promotion path kept cheap: **generated columns** extracting hot JSONB paths into real (indexed, statistics-bearing) columns — the mechanism that makes "we now query this field constantly" a migration-free evolution rather than a redesign, and the expand/contract discipline's best friend at this layer.

## The toolkit: indexing and querying without folklore

The operational knowledge that separates working hybrids from slow ones: **GIN indexes** are the JSONB workhorse — supporting containment (`@>`) and existence queries across the document — with the sizing caveat that a whole-document GIN on large payloads is a write-amplification and space cost (the index-cost accounting from indexing practice applies with interest; the `jsonb_path_ops` variant trades query flexibility for a substantially smaller index, and is the right default when containment is your shape). **Expression indexes on specific paths** (`(data->>'customer_ref')`) serve the equality/range lookups on known-hot fields at ordinary B-tree cost — and pair with the generated-column promotion when the field graduates to constraint-participation. **The planner honesty problem**: JSONB path selectivity is largely opaque to statistics, so plans against document predicates lean on defaults — the practical responses are the promotion path above for anything plan-sensitive, and the plan-reading discipline pointed at any query mixing JSONB predicates with joins (the misestimate-driven nested-loop disaster has a documented JSONB variant). **Query ergonomics**: the path language (`jsonb_path_query`, the `->`/`->>`/`#>>` operator family) covers extraction and filtering; lateral joins plus `jsonb_array_elements` un-nest arrays into relational shape for aggregation (the window-function world composes from there); and updates use `jsonb_set`-style surgical mutation — with the transactional note that a JSONB update rewrites the whole value (the MVCC row-rewrite economics from performance practice: hot, frequently-mutated subfields in a large document are a write-amplification pattern arguing for promotion to columns or a separate narrow table).

## The discipline line: schema-on-write lives in the application now

JSONB's real risk is governance, not performance: the database stops enforcing document shape, and the shape doesn't stop mattering — it just moves to the application boundary, where it's either engineered or entropic. The engineered version imports the contract disciplines wholesale: **validation at every write path** (the Pydantic/Zod-class schema-at-the-boundary rule — nothing enters the JSONB column unvalidated, because the column will happily store the typo'd field name forever), **versioned payload schemas** (a `schema_version` key inside the document, with the migration story for old versions decided — lazy-upgrade-on-read or backfill, per the data-migration playbook — because five years of accumulated shapes without versioning is the archaeology that makes teams swear off the whole approach), **shape monitoring as data quality** (the profiling checks from data-quality practice pointed at key-frequency and type-consistency across the column — drift between what the application writes and what analysts assume is the silent breakage genre), and — where the invariant is strong enough — **check constraints on JSONB** (Postgres can enforce structural rules against the document; used sparingly, it's the belt to the application's suspenders for the fields that must exist). The analytics seam completes the picture: JSONB columns flow into the lakehouse via the CDC rails like everything else, but the *flattening decision* (which paths become warehouse columns) should track the same promotion logic — the dimensional model wants typed attributes, and "we'll parse the JSON in every dashboard query" is the modeling debt from warehouse practice, imported.

The closing calibration: JSONB earned its place by making the document-vs-relational war unnecessary — but the peace terms matter. Spine in columns, variance in documents, hot paths promoted via generated columns, GIN where containment is the shape, validation and versioning at the write boundary, and the promotion/demotion review run periodically like the modeling decision it is. The flexibility was never free; it was *relocated* — and the teams that know where it went are the ones whose hybrid schemas are still legible at year five.
