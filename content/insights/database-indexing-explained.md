Database indexing occupies a strange knowledge niche: every backend engineer knows indexes make queries fast, most can add one, and surprisingly few can predict *which* queries an index will and won't serve — which is why production systems accumulate both missing indexes (the slow query everyone tolerates) and useless ones (the write-amplifying dead weight nobody audits). The gap closes with one mental model, held firmly: the index as a sorted structure, read the way the query planner reads it.

## The mental model: a sorted phone book with pointers

A B-tree index — the default nearly everywhere — is a balanced tree keeping entries **in sorted order by the indexed value(s)**, each entry pointing at its table row. Every capability and every limitation flows from "sorted": an index on `email` answers `email = ?` in a handful of page reads (tree descent, logarithmic), serves `email > ?` and `email BETWEEN` (walk the sorted range), serves `ORDER BY email` without sorting (it's *already* sorted), and serves prefix patterns `LIKE 'smith%'` (a range in disguise) — but does nothing for `LIKE '%smith'` (sorted order is useless for suffixes), nothing for `lower(email) = ?` (the index stores `email`, not `lower(email)` — function-wrapped columns need *expression indexes* matching the exact expression), and nothing efficient for "all rows where email is one of 40% of the table" (below, on selectivity).

The second half of the model is the read path's cost structure: an index lookup finds *pointers*; fetching the actual rows costs additional random I/O per row. This one fact explains the two planner behaviors that most confuse people. **Why did it ignore my index?** Because for low-selectivity predicates (matching a big fraction of the table), thousands of random row-fetches cost more than one sequential scan — the planner is usually right, and the fix is a more selective predicate or a better index, not planner hints. **What's a covering index?** One that contains every column the query needs (via composite keys or INCLUDE columns), so the row fetch never happens — the query is answered entirely inside the index, which is why covering hot queries is one of the biggest single wins available.

## Composite indexes: the leftmost-prefix rule and the design recipe

Multi-column indexes are where engineering judgment concentrates, and one rule governs them: a composite index on `(a, b, c)` is sorted by `a`, then `b` within `a`, then `c` within that — so it serves queries filtering on `a`, on `a,b`, on `a,b,c` (leftmost prefixes), but is largely useless for queries touching only `b` or `c` (their order exists only *within* each `a`). The recipe that follows for designing an index for a query: **equality columns first, then the range or sort column** — `WHERE tenant_id = ? AND status = ? AND created_at > ? ORDER BY created_at` wants `(tenant_id, status, created_at)`; the equality columns pin a contiguous block, and within it, `created_at` is sorted — filter and order both served, no sort step. Put the range column earlier and everything after it degrades (once you range over a column, deeper columns' order is useless).

Corollaries with daily relevance: the index on `(a, b)` makes a separate index on `(a)` redundant (drop it); column *order within the index* matters far more than most schema reviews notice; and "one index per column, let the database combine them" (bitmap-AND exists but underwhelms) is a weak substitute for one well-designed composite per critical query shape. Design indexes *from the query workload* — the top slow queries by total time — not from the schema's aesthetics.

## What indexes cost: the accounting nobody does

Every index is a second data structure that **every write must maintain**: each INSERT touches every index on the table; UPDATEs touch every index whose columns changed (and in Postgres, thanks to its MVCC row-versioning, potentially more than that — one reason hot-updated tables want lean indexing). Ten indexes on a high-write table can mean the write does 10× the structural work you think it does — plus buffer-cache pressure (index pages compete with data pages for memory) and storage. The operational hygiene that follows: **audit for unused indexes** (every engine exposes usage counters — `pg_stat_user_indexes` and friends; unused indexes on write-hot tables are pure tax, and their removal is free performance), audit for *redundant* ones (prefix-subsumed as above), and treat "add an index" PRs with the same cost-consciousness as "add a dependency" ones. Indexes are not free speed; they're a purchase of read performance with write currency, and the exchange rate varies by table.

## Beyond the B-tree, briefly

The specialized structures earn their keep in their niches: **partial indexes** (index only rows matching a predicate — `WHERE status = 'active'` — small, hot, and precisely aimed at queries with the same predicate; chronically underused); **expression indexes** (for the `lower(email)`, date-truncation, and JSON-extraction predicates your queries actually use); **GIN-class inverted indexes** for containment questions (full-text, JSONB, arrays — "which rows contain X" is the inverted index's home game and the B-tree's nightmare); **BRIN-class block-range summaries** for huge naturally-ordered tables (append-only time series — tiny indexes, great for time-range scans); and the vector indexes (HNSW-class) of the embedding era, which come with *approximation* semantics — recall/latency trade-offs — that deserve conscious tuning rather than default acceptance. The selection principle: name the query shape first, then pick the structure built for it.

## The working loop

Index work is empirical or it's guesswork. The loop: capture the workload's expensive queries (slow-query logs, `pg_stat_statements`-class aggregation — sort by *total* time, not just worst-case, because the 5 ms query run a million times an hour outranks the 2-second nightly one); read the plan (`EXPLAIN ANALYZE` — learn to spot the sequential scan on the big table, the sort that an index order would erase, the row-estimate wildly off from reality signaling stale statistics); design the minimal index for the shape; verify the plan changed *and* the metrics moved; and re-audit quarterly, because workloads drift and last year's crucial index is this year's write tax. Keep statistics fresh (autovacuum/analyze health is index performance in Postgres), and remember the planner is a cost model — it's only as good as its statistics, and "the database is dumb" is almost always "the statistics are stale" or "the index doesn't serve the shape."

The compact takeaway: sorted-structure mental model, equality-then-range composite design, covering indexes for the hottest paths, partial/expression indexes for the predicates you actually write, write-cost accounting on every addition, and an empirical loop instead of superstition. That's the whole craft — and it remains, byte for byte, the highest-ROI performance discipline in ordinary backend systems: no rewrite, no infrastructure, one DDL statement, thousandfold speedups, still slightly magical every time.
