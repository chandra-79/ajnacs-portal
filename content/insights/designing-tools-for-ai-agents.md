A new consumer arrived at the enterprise API surface, and it reads differently than the last one: the AI agent — the LLM-driven system that selects and invokes tools to accomplish tasks — is becoming a first-class caller of internal and external APIs (through the MCP-style protocol layer and the function-calling interfaces the model vendors standardized), and it fails in ways human developers don't. A developer reads your docs once, builds a mental model, and encodes it in code that behaves identically forever; an agent re-reads your tool descriptions *every session*, reasons probabilistically about what to call, and improvises under ambiguity. Designing for this consumer is a discipline with emerging rules — most of which turn out to be classical API design principles, enforced with new severity, plus a safety tier the classical world never needed.

## The description is the interface

An agent selects tools by reading their names, descriptions, and parameter schemas — which promotes documentation from developer courtesy to *runtime control surface*: the description **is** the dispatch logic. The disciplines that follow: **names and descriptions written for disambiguation** (the agent choosing between `search_orders` and `list_orders` has only your prose — describe *when to use this tool and when not to*, with the boundary cases explicit, because every ambiguity you leave is a misroute you'll observe at volume), **parameter schemas that constrain rather than suggest** (enums over free strings, formats declared, required-versus-optional honest — the schema-first validation disciplines, now doing double duty as the agent's guardrails: a parameter the schema permits is a parameter some session will send), **examples in the description** (few-shot steering embedded at the tool boundary — the highest-leverage documentation genre for this consumer), and **operation granularity tuned to task shape** (the classical REST-resource decomposition can be wrong for agents: forty fine-grained calls to accomplish "reschedule the meeting" burns context and multiplies error surface — the emerging pattern is *task-shaped composite tools* for the common workflows alongside the primitive operations, which is the BFF insight applied to a nonhuman frontend).

**Errors graduate from diagnostics to steering**: the agent reads error messages and *adjusts its next attempt*, which makes the error-contract disciplines load-bearing in a new way — errors should say what was wrong *and what to do* ("date must be ISO-8601; you sent '3rd of March'" produces self-correction; "400 Bad Request" produces flailing retries), retryability must be explicit (the agent's retry judgment is only as good as your taxonomy), and the response should resist the temptation to be terse: this consumer has no Stack Overflow, only what you return.

## The safety tier: capability design for a credulous caller

The agent security chapter established the frame — the agent is a confused-deputy risk by construction (it reads untrusted content and holds your credentials) — and the tool layer is where mitigations become concrete: **scope tools to tasks, not products** (the least-privilege rule at tool granularity: the triage agent gets `create_draft`, not `send_email` — every capability in the manifest is attack surface for whatever prompt-injection reaches the context), **consequential actions get structural friction** (the irreversibility ladder from automation practice: read tools free; mutating tools idempotent with dry-run modes — the agent that can preview "this will cancel 400 orders" before executing is an agent whose mistakes are catchable; destructive/external tools behind human confirmation with the *actual effect* displayed, per the approval-UI honesty rules), **server-side enforcement of everything** (the agent asserting "the user approved" is not authorization — the tool's backend checks the caller's actual entitlements per the authorization models, treats agent traffic as its own principal class in the audit stream, and rate-limits it like the retry-capable automation it is), and **idempotency keys as a default parameter** (agents retry ambiguously-failed calls as a matter of policy — the duplicate-effect protections stop being best practice and become the assumption).

The operational rim mirrors every new-consumer story: **observability per tool per session** (which tools get called, with what argument distributions, failing how — the tool-call telemetry is simultaneously your UX research for descriptions, your misroute detector, and your security monitoring; the argument that arrives outside the expected distribution is either a description bug or an injection probe), **evaluation suites for the tool surface** (the eval-gate discipline: scripted task scenarios asserting the agent selects and sequences tools correctly, run against every description change — because tool descriptions are prompts, and prompt changes are behavior changes needing regression coverage), and **versioning with the deprecation machinery** (agents don't read changelogs; the old tool name must keep working or explicitly redirect — the API-evolution rules with a consumer that never migrates itself).

The closing observation is the reassuring one: almost everything above — unambiguous contracts, constrained inputs, actionable errors, idempotent mutations, least-privilege scoping, honest documentation — is what this series has argued APIs owed *human* consumers all along. The agent era doesn't introduce a new design philosophy; it removes the compensating layer (the patient developer who reads around your ambiguities and hardcodes the workarounds) that let mediocre API design survive. The APIs that agents use well are the APIs developers always wished for — which makes agent-readiness less a new requirement than an audit, conducted by your most literal-minded consumer, of promises your interface was already supposed to keep.
