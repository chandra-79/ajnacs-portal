Between your origin and every user sits a volunteer distributed cache of planetary scale — browser caches, corporate proxies, CDN edges — that will store and serve your responses according to rules you declare in a handful of headers. Most teams declare those rules by framework default and cargo cult, which produces the twin failure modes seen everywhere: assets that *could* be cached forever getting refetched on every visit (performance left on the table), and responses that must *never* be shared getting cached somewhere surprising (the private-data-in-shared-cache incident genre). HTTP caching is a small, learnable contract — five headers and two mental models — that runs a shocking fraction of the web's performance.

## The two models: freshness and validation

**Freshness** answers "may this be served without asking the origin?" — `Cache-Control: max-age=3600` grants an hour of serve-from-cache autonomy; within it, the request never leaves the cache (zero latency, zero origin load); after it, the response is *stale*, not deleted — which is where the second model begins. **Validation** answers "is my stale copy still good?" — the origin sends a validator with the response (**ETag**, a content fingerprint, or `Last-Modified`), and the client's revalidation request carries it back (`If-None-Match`); the origin answers either **304 Not Modified** (headers only, no body — the cheap answer that says "your copy stands") or a fresh 200. The composite is the machine: fresh → serve locally; stale → revalidate cheaply; changed → transfer fully. Most caching misconfiguration is using one model where the other belongs — long `max-age` on mutable content (the "why is the old version still showing" ticket) or zero caching with no validators on stable content (full re-transfers of unchanged bytes forever).

## The patterns that cover 90% of cases

**Immutable fingerprinted assets** — the web-performance workhorse: build pipelines emit content-hashed filenames (`app.3f2ab1.js`), served with `Cache-Control: public, max-age=31536000, immutable` — cache forever, *because the URL changes when the content does*; the HTML that references them carries the short leash instead. This pattern (versioned-URL-plus-immutable) is the static half of every framework's deployment story and the reason "cache invalidation is hard" mostly stopped applying to assets: you don't invalidate — you address.

**HTML and API responses** — the mutable tier: short-or-zero freshness with validators (`no-cache` means *always revalidate*, not *never store* — the misreading that costs teams 304s they could have had; *never store* is `no-store`), and the modern refinement that CDNs made standard: **`stale-while-revalidate`** — serve the stale copy instantly while refreshing in the background — which buys cache-hit latency with bounded staleness (a declared staleness budget, per the derived-data honesty rules), and its sibling `stale-if-error` (stale beats 500 — the graceful-degradation posture in one directive).

**The API-specific dividend:** ETags on API responses do double duty — the caching 304s, and **optimistic concurrency** via `If-Match` on writes (the lost-update guard from pagination-and-session practice — same validator, second job). Conditional requests are the API's cheapest bandwidth and consistency tool, and most APIs ship neither.

## The shared-cache layer: keys, variance, and the private-data rule

CDN and proxy caching adds the questions browsers don't ask: **What's the cache key?** — by default the URL, which means everything that *changes the response* must either be in the URL or declared via **`Vary`** (the header that says "the response depends on Accept-Encoding / Accept-Language / this-custom-header") — and every `Vary` dimension multiplies cache fragmentation (Vary on `Cookie` or `User-Agent` is effectively "don't cache" wearing a technical costume; the compression negotiation from compression practice rides `Vary: Accept-Encoding` as the one universal, well-supported case). CDN-level cache-key configuration (which query params matter, which headers, normalized how) is where hit rates are won: unnormalized keys (`?utm_source=...` fragmenting the cache per marketing campaign) are the classic silent hit-rate killer, findable in one afternoon of CDN analytics.

**The private-data rule** deserves its own paragraph because its failures make headlines: `Cache-Control: private` (browser-only) versus `public` (shared caches welcome) is the entire boundary between "cached on the user's device" and "cached on infrastructure that serves other users" — and authenticated, personalized responses must carry `private` (or `no-store` for the sensitive tier) *and* your CDN must be configured to respect it. The incident pattern is depressingly stable: a caching layer added in front of an app that assumed no shared cache, session-authenticated pages cached publicly, user A served user B's account page. Every response containing personal data needs its cache policy *reviewed as a security control* (the privacy-engineering lens), and the edge configuration audited against it — because default CDN behaviors on ambiguous headers vary, and ambiguity at this boundary is exposure.

**Purge is the escape hatch, not the strategy:** CDN invalidation APIs (purge-by-URL, by tag/surrogate-key — the tagging pattern that lets "purge everything about product 123" be one call) handle the *exceptional* update; architectures that rely on purge for routine correctness have chosen the hardest consistency model available (distributed invalidation) when addressing (fingerprints) or short-TTL-plus-SWR would have deleted the problem. The placement mirrors every derived-store discipline: the cache is a projection; design for rebuild-by-expiry first, targeted invalidation second, and never for "we'll purge and hope."

The audit worth running this quarter, because it's cheap and always finds money: pull the CDN hit-rate report by content type; check the top misses for unnormalized keys and missing freshness headers; grep the API responses for absent ETags; confirm every authenticated route's `Cache-Control` says what the security model needs; and verify the asset pipeline emits immutable fingerprints. Five headers, two models, one afternoon — and the planetary cache you were already renting starts working for you at the rate it always could.
