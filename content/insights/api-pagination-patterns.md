Pagination is the API design decision most teams make by copying whatever their framework scaffolds — `?page=3&per_page=50` — and most regret at scale in two predictable ways: the database query behind page 40,000 melts (offset pagination's dirty secret), and clients discover items skipped or duplicated as concurrent writes shift the pages under them (the consistency problem nobody documented). Pagination is really two contracts in one — a *performance* contract with your database and a *consistency* contract with your clients — and getting both right is a page of knowledge that saves a redesign.

## Offset pagination: fine until it isn't

`LIMIT 50 OFFSET 200000` reads as "jump to page 4,001" and executes as "**produce and discard 200,000 rows**, then return 50" — offset is a skip-counter, not an address, and the database must walk everything skipped (index or not) to know where page 4,001 begins. Cost grows linearly with depth; deep pages become the slow queries that dominate the total-time profile (the workload-analysis lens finds them fast), and the crawler that walks your catalog back-to-front becomes an accidental load test of exactly the worst case.

The consistency flaw is subtler and bites shallower: pages are defined by *position*, and positions shift. A row inserted (or deleted) ahead of a client's progress renumbers everything behind it — the client paging through sees an item twice, or never (the row that slid from page 6's tail to page 7's head between requests, or vice versa). For a human flipping through a dashboard, harmless; for anything *synchronizing* — the export job, the integration walking all records — it's silent data loss wearing a 200 status.

Offset's legitimate niche survives: shallow, human-facing, jump-to-page-N interfaces (admin tables, search results where nobody visits page 400 and Google's own results famously don't go much deeper) — with a documented depth cap (reject or clamp beyond page ~100), which converts the melt-down case into a 400 and an invitation to use the real mechanism.

## Cursor pagination: position as value, not count

The grown-up pattern: each page returns an **opaque cursor** encoding *where the page ended* — not "you've seen 200,000 rows" but "the last row was (created_at=…, id=…)". The next request says "continue after this point," and the database executes a **keyset query**: `WHERE (created_at, id) > (?, ?) ORDER BY created_at, id LIMIT 50` — an index seek to the exact position plus a scan of 50 rows, at *constant cost regardless of depth*. Page one and page one million cost the same. The implementation rules that make it sound: **the sort key must be unique and stable** (hence the tiebreaker id appended to any non-unique ordering — ties without a tiebreaker cause skips or repeats at page boundaries, the classic keyset bug), **the composite index must match the sort** (the equality-then-range index design rules, serving pagination), and **the cursor should be opaque and signed/versioned** (it's serialized implementation detail; clients that parse it will couple to your index choices — the API-evolution discipline says encode, encrypt-or-sign, and reserve the right to change the innards).

Consistency improves structurally: cursors anchor to *values*, so inserts and deletes elsewhere don't shift the client's position — no duplicates, no skips among unchanged rows. What cursors *don't* promise is a snapshot: rows modified after you passed them are missed, rows behind your cursor reflect their latest state — the pagination equivalent of read-committed, and the honest thing to document. (True snapshot pagination — consistent as-of-a-moment iteration — requires versioned storage or explicit snapshot tokens, and it's the moment to ask whether the client's actual need is the next section's pattern instead.) The ergonomic trade: no random access ("jump to page 37" has no meaning), which is why real designs often pair a capped-offset mode for humans with cursor mode for machines — two documented modes for two audiences beats one mode failing both.

## The sync endpoint: what deep pagination usually wanted to be

The consumer paging through *everything, repeatedly* — the nightly integration, the search-index rebuilder, the mobile app refreshing local state — isn't paginating; it's **replicating**, and pagination is a bad replication protocol. The pattern that serves the need honestly: a **changes/sync endpoint** — "give me everything modified since cursor/timestamp T, including deletions (tombstones), in a stable order, page by cursor within that" — turning the full re-walk into an incremental delta feed (the CDC insight, surfaced as API design; the webhook-reconciliation loop's pull-side twin). Every API whose access logs show clients re-walking the full collection on a schedule is being asked for this endpoint in the least efficient possible dialect. Design notes: monotonic, indexed change-markers (an `updated_at` with an index, or better a sequence), tombstones retained for a documented horizon (the deletion-propagation lesson), and idempotent consumption assumed (at-least-once weather, as everywhere).

## The contract details clients actually depend on

The remaining craft is documentation-as-interface: return the cursor *and* an explicit `has_more`/next-link (clients guessing "short page means done" break on filtered queries — an empty page with `has_more: true` is legal and *will* happen); put page-size limits in writing with server-side clamps (the unbounded `per_page=100000` is a self-service DoS, per the rate-limiting disciplines — and cost-aware limits should count page size); document the ordering guarantee precisely ("descending by creation, stable" — because clients build merge logic on it); version cursors so a schema change invalidates them gracefully (a clear 400 "cursor expired, restart" beats silently wrong continuation); and state the consistency class in the docs — positional (offset), value-anchored (cursor), or snapshot/delta (sync) — because the client engineer deciding whether they can trust a full walk is making a correctness decision with your paragraph, or without it.

The summary that fits in a design review: offset for shallow human browsing with a depth cap; keyset cursors — unique sort key, matching index, opaque token — as the default for everything programmatic; a sync/changes endpoint the moment any client's real job is replication; and the consistency promise written down in every case. Pagination is one of those small interfaces where the cheap version and the correct version diverge invisibly at first and expensively later — and where a page of discipline, applied on day one, is the difference between an API that scales with its consumers and one that teaches them, incident by incident, exactly how it was scaffolded.
