There's a reliable tell that separates engineers who learned SQL as "SELECT-WHERE-GROUP BY" from those who learned what it became: the first group exports data to pandas — or worse, loops in application code — for problems like running totals, top-N-per-group, deduplication by recency, and month-over-month deltas; the second group writes one query with an `OVER` clause and lets the database do what databases do best. Window functions have been standard SQL for two decades and first-class in every serious engine, and they remain the single highest-leverage SQL feature that working engineers systematically underuse. The gap is a mental model, and it fits in a page.

## The model: aggregate context without collapsing rows

`GROUP BY` answers questions by *collapsing* rows — you get the sum per customer, but you lose the orders. Window functions answer the other family of questions: **every row stays, and each row gains context computed over a related set of rows** (its "window"). `SUM(amount) OVER (PARTITION BY customer_id)` gives every order row the customer's total *alongside* the order's own details — the collapse-free aggregate. Three clauses define the window: **PARTITION BY** (which rows are peers — the per-group boundary), **ORDER BY** (their sequence, which unlocks everything positional), and the **frame** (which peers are visible: everything so far for running totals, a sliding range for moving averages, the whole partition for shares-of-total). Once the model clicks — *each row asks a question about its neighborhood* — the patterns write themselves.

## The workhorse patterns

**Ranking and top-N-per-group** — the query that defeats GROUP BY entirely ("the three most recent orders *per customer*") is the canonical window idiom: `ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC)` wrapped in a subquery, filtered to `rn <= 3`. Know the trio's semantics: `ROW_NUMBER` (arbitrary tiebreak — exactly one winner), `RANK` (ties share a rank, gaps follow), `DENSE_RANK` (ties share, no gaps) — the difference between them is the difference between "a top-3 list" and "everyone in the top three scores," which is a business question wearing a function name.

**Deduplication by recency** — the same idiom pointed at data quality: partition by the natural key, order by the freshness signal, keep `rn = 1`. This is the standard answer to CDC-fed tables and event streams with duplicates (the at-least-once weather from every pipeline discipline, mopped up in one query), and it belongs in every data engineer's reflexes.

**Running and windowed aggregates** — `SUM(...) OVER (PARTITION BY account ORDER BY date)` for running balances; frames (`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW`) for moving averages; `amount / SUM(amount) OVER (PARTITION BY category)` for share-of-total. The frame-default footnote that bites: with ORDER BY present, the default frame is *range-to-current-row* — fine for running totals, surprising when peers tie; specify frames explicitly in anything load-bearing.

**LAG/LEAD: the row that sees its neighbors** — period-over-period deltas (`amount - LAG(amount) OVER (...)`), time-between-events (this login versus the previous), and change detection ("price differs from yesterday's") — all without self-joins, which is what these replaced: the old idiom joined the table to itself with an off-by-one date dance that was slower to run and worse to read.

**Sessionization: the composite masterclass** — the gaps-and-islands problem ("group events into sessions separated by 30+ minutes of silence") is where windows compose into real power: LAG computes the gap to the previous event; a CASE flags session starts; a running SUM over the flags assigns session IDs — three windowed steps, pure SQL, and the foundation of funnel and engagement analytics everywhere (the same computation streaming engines perform with session windows, done batch-side in the warehouse). Learning this one pattern teaches the composition instinct that unlocks the rest.

## Performance and placement

Window functions are executed by sorting (or exploiting existing order): each distinct `PARTITION BY / ORDER BY` combination in a query is potentially its own sort of the input, so the performance disciplines follow directly — **align windows with each other** where possible (several functions sharing one window spec share one sort; five functions with five specs are five sorts), **filter before windowing** (windows compute over their full input; a WHERE that runs first shrinks every sort — but remember you *can't* filter on a window result in the same query level, hence the ubiquitous subquery/CTE wrapper, and note `QUALIFY` — the dedicated post-window filter clause that warehouses and DuckDB-class engines support — which cleans up the idiom where available), and **feed them with indexes** (an index matching the partition/order columns lets the engine skip the sort entirely — the composite-index design rules, serving analytics). For the big-data tier: window functions are first-class across the warehouse engines and their per-partition parallelism is exactly the consistent-hashing intuition — partitions distribute, but a window over *one giant partition* (the whale tenant again) serializes onto one worker, which is the skew diagnosis when the "simple ranking query" runs forever.

The placement judgment — SQL versus dataframe versus application code — has shifted decisively toward SQL as the engines converged on full window support: computation next to the data beats shipping the data to the computation (the eternal rule), the query optimizer sees your whole intent, and the logic lives where every consumer — pipeline, dashboard, notebook, the AI assistant writing next quarter's variant — can read one canonical definition. The pandas escape hatch remains legitimate for the genuinely procedural; the running total never was.

The closing pitch to the SELECT-WHERE-GROUP BY generation: window functions are not advanced SQL — they're *the other half* of SQL, the half that answers questions about rows in context, and the half the analytical world runs on. One afternoon with PARTITION BY, one internalized top-N idiom, one sessionization exercise — and a career's worth of "export it and loop" detours quietly retire into single queries that were always waiting there in the standard.
