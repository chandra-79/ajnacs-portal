Every API team eventually learns the asymmetry: the quality of the API is discovered slowly, but the quality of its documentation is discovered in the first ten minutes — and for the developer deciding between your platform and an alternative, those ten minutes are frequently the whole evaluation. Documentation isn't a description of the product; for APIs and internal platforms alike, **it is the user interface** — the surface through which every capability is discovered, understood, and adopted. Teams that staff and measure it accordingly win integrations; teams that treat it as the chore after the sprint produce the support tickets and the Slack archaeology that pass for documentation everywhere else.

## The architecture: four kinds of docs, four different jobs

The most useful organizing insight (popularized as the Diátaxis framework) is that "documentation" is four products with conflicting requirements, and mixing them produces the mush that serves nobody: **tutorials** (learning-oriented: take a beginner to a working result — one golden path, zero decisions, guaranteed success; this is where time-to-first-call lives), **how-to guides** (task-oriented: "accept a payment with a saved card," "rotate a webhook secret" — recipes for people who know the basics and have a job to do; the highest-traffic tier in mature docs), **reference** (information-oriented: every endpoint, field, error, and limit — complete, accurate, generated, searchable; consulted, never read), and **explanation** (understanding-oriented: the concepts — idempotency model, auth architecture, rate-limit philosophy — that make the reference *make sense*). The recurring failure is writing only reference (complete and unusable for newcomers) or only tutorials (welcoming and useless by week two); the audit question for any docs set is which of the four quadrants is starved — and it's usually how-to guides, because they require knowing the users' actual tasks, which requires talking to them.

## The engineering: docs as a build artifact

Documentation that lives apart from code drifts from truth at the speed of deployment, so the mature pipeline treats docs as code with the same disciplines: **reference generated from the contract** (OpenAPI/GraphQL schemas as the single source — with the crucial caveat that generation guarantees *coverage*, not *quality*: a generated page of undescribed fields is technically complete and practically useless; the human work is descriptions, examples, and error semantics in the spec itself, reviewed like code because it is code), **examples that are tested** (every snippet in CI — compiled, executed against a sandbox, asserted; nothing erodes trust faster than the quickstart that doesn't run, and nothing prevents it except making broken examples break the build), **docs changes in the same PR as behavior changes** (the review-gate question "does this change the contract? then where's the docs diff?" — enforced culturally or mechanically), and **versioning that matches the API's** (docs for the version the reader runs, deprecations visible with dates and migration paths — the API-evolution discipline surfaced where users actually look).

The experiential layer that separates good from great is *runnable-ness*: the interactive explorer ("try it" against a sandbox with the reader's own test key pre-filled), copy-paste-ready snippets in the reader's language (generated per-language from the spec, so they're never stale), and sandbox environments where the first call can't hurt anything — because the real product being sold in the first ten minutes is *confidence*, and nothing builds it like a 200 response.

## The measurement: docs have vitals too

"Good docs" without metrics is a vibe; the operational versions: **time-to-first-successful-call** (the north star for external APIs — instrument the funnel from docs landing to first authenticated 200 on a sandbox; every minute shaved shows up in adoption), **search-and-fail analytics** (what readers search for and don't find is the docs backlog, ranked by demand — the top failed queries are next quarter's how-to guides), **support-ticket taxonomy** (every recurring "how do I" ticket is a docs gap with a cost attached; mature teams close the loop by requiring a docs fix alongside frequent-ticket resolutions — the incident-review pattern applied to confusion), and **page-level feedback with follow-through** (the thumbs-down button matters only if someone triages it). For internal platforms the same logic applies with different stakes: the paved-road adoption that platform teams are measured on is rate-limited by exactly these funnels, and the internal docs portal deserves the same telemetry as the external one.

## The AI-era addendum: your docs have new readers

Two shifts are quietly restructuring the discipline. First, **a growing share of documentation consumption happens through models** — developers ask their assistant, the assistant reads (or was trained on) your docs, and the answer arrives synthesized; docs that are structured, example-rich, and semantically clear get represented accurately, while docs whose truth lives in tribal knowledge get hallucinated around. Making documentation machine-legible — clean structure, canonical URLs, llms.txt-style conventions as they settle, accurate OpenAPI as the ground truth — is becoming distribution strategy, not just hygiene. Second, **AI assistance changed docs production economics** — drafts, translations, per-language snippet generation, and consistency passes are cheap now, which moves the human bottleneck to exactly where it should be: knowing the user's task, deciding what's true, and curating ruthlessly (the documentation-lifecycle discipline — owners, review dates, deletion as celebrated activity — because generated volume without curation is negative-value at scale, in docs as everywhere else).

The summary for the platform review: treat docs as the product surface they are — four quadrants deliberately staffed, reference generated from tested truth, examples that run, funnels measured from landing to first success, tickets feeding the backlog, and machine readers planned for. The teams that internalize this stop asking "did we document it?" and start asking the product question — *"can a stranger succeed with this, alone, in ten minutes?"* — because that, measurably, is where adoption is decided.
