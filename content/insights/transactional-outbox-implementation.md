The transactional outbox is this series' most-referenced supporting actor — the standard answer to the dual-write problem (the service that must update its database *and* publish an event, atomically, when no transaction spans both) — and its diagram is deceptively complete: write the business change and the outgoing message to an `outbox` table in one transaction; a relay reads the table and publishes; downstream consumers dedupe. The diagram is correct. The production version has a half-dozen decisions the diagram doesn't show, and each has a wrong default that surfaces as an incident months later.

## The write side: what goes in the box

The outbox row is a message contract frozen at commit time, and its design inherits the event-governance disciplines: **a unique message ID minted at write** (the idempotency key every downstream dedupe will rely on — stable across retries and committed with the event, never regenerated by the relay), **a payload with explicit semantics** (a historical event should capture its required state at commit; a deliberate current-state notification can instead carry an identifier, but the relay must not silently re-query mutable tables to enrich historical content — the row it reads may be older than current state, and the join-at-publish reintroduces exactly the read-your-own-write races the pattern exists to kill; snapshot what the event needs at commit, per the events-carry-state principle), **event type and schema version as first-class columns** (the registry-compatibility disciplines apply to outbox payloads fully — this table is a message bus wearing a schema), **the aggregate/entity ID as an explicit column** (ordering's foundation, below), and **occurred-at as event time** (the two-clocks honesty: business time and source observation time are distinguished; record commit time only when the source actually provides it, because the consumers' watermark logic will eventually ask).

The write discipline that keeps the pattern honest: the outbox insert happens **in the same transaction as the business change, always, enforced structurally** — a repository/domain-event layer that collects events during the unit of work and flushes them with it (the hexagonal seam doing the work), never an application convention ("remember to also insert the event") that decays into the exact dual-write gap the pattern was bought to close.

## The relay: the component with all the sharp edges

The relay's job — table to broker, reliably — decomposes into the decisions that matter:

**Polling versus CDC.** The polling relay (SELECT unpublished ORDER BY id LIMIT n, publish, mark) can be simple and portable when its claim, retry and ordering protocol is specified — with the `FOR UPDATE SKIP LOCKED` idiom preventing concurrent row claims while locks are held, without by itself guaranteeing publication order (the job-queue pattern, verbatim) — at the cost of poll-interval latency and steady read load. The CDC relay (the log-tailing tier reading outbox inserts from the WAL — the Debezium-outbox integration productizes exactly this) can reduce polling latency and avoid repeated table scans, while still imposing decoding and retention costs, at the price of the CDC platform's operational surface (the replication-slot vigilance from CDC practice). The honest default: polling for modest volumes and simpler estates (its latency floor — sub-second at reasonable intervals — satisfies most integration needs); CDC where the outbox is high-volume or the platform already runs the rails.

**Delivery semantics: at-least-once, embraced.** The relay *will* republish (the crash between publish and mark-published is the designed-for case), so the end-to-end effect guarantee must be scoped separately from delivery attempts: the message ID plus consumer-side dedup (the inbox-table discipline) is the contract, and the relay's job is *never losing* rather than never duplicating. The corollary that surprises: **mark-as-published is itself a dual write** (publish to broker, then update the table — a crash between them re-sends), which is fine *because* the ID makes re-sends harmless; relays that try to be clever here (transactional marks against the broker) buy complexity the consumer-side dedup already paid for.

**Ordering: per aggregate, not global.** The guarantee consumers actually need is "events for order 123 arrive in commit order," delivered by publishing with the aggregate ID as the partition key (the per-key ordering from messaging practice) and relaying in commit order (a documented transaction order; sequence allocation alone is not commit order). Global ordering across aggregates is neither promised nor needed — and relay parallelism should shard *by aggregate* (workers own key ranges) rather than by arbitrary batch, or the per-aggregate guarantee quietly breaks under the concurrency that was supposed to be safe.

**Table hygiene: the outbox is a queue wearing a table.** Unmanaged, it grows forever and its polling query degrades (the unbounded-table pathology); the disciplines: published rows deleted or archived according to an explicit recovery, audit and replay retention policy, the partition-by-time trick where volume justifies (drop old partitions instead of DELETE churn — the vacuum-pressure mercy for the MVCC engines), and the *unpublished backlog* as the vital sign: *outbox lag* — oldest-unpublished age and backlog depth — alarmed with the absence-detection seriousness of any pipeline, because a stalled relay is silent data divergence in progress: the database moved on, the world didn't hear, and every minute widens the reconciliation.

The monitoring rim completes it: end-to-end publish latency (commit-to-broker, the SLO consumers design against per the staleness-budget honesty), relay error taxonomy (poison messages — the row that fails serialization forever — diverted to a dead-letter state with alerting rather than wedging the stream, per the poison-pill patterns), and the periodic reconciliation count (outbox-published versus broker-received over a window — the trust-but-verify loop that catches the silent partial failure every at-least-once pipe eventually manufactures).

The closing calibration: the outbox is the rare pattern that's both genuinely simple and genuinely subtle — one table, one relay, and a handful of decisions (self-contained payloads, structural writes, per-aggregate ordering, aggressive cleanup, lag alarms) that separate the implementations that quietly carry a company's integration traffic from the ones that generate the "events stopped flowing Tuesday, nobody noticed until Friday" incident. It earns its ubiquity in this series honestly: it's the smallest correct answer to distributed systems' oldest question — how to tell the truth *and* tell someone about it, atomically — and like most smallest-correct answers, the correctness lives in the details the diagram leaves out.

## Worked delivery ledger: one event, several attempts

Consider a hypothetical batch of 100 committed business transactions, each of which inserts one outbox event in the same local database transaction. The relay publishes all 100 events. After the broker accepts the batch, the relay crashes before recording publication status for ten of them. On restart it republishes those ten with their original message identifiers. The broker has observed 110 delivery attempts representing 100 unique events.

A consumer that atomically records the event identifier with its local business mutation applies 100 unique effects and recognizes ten duplicates. This is the figure's accounting: 100 committed outbox rows, 110 delivery attempts and 100 unique applied effects. The counts are synthetic and assume that every attempt eventually reaches the consumer, that deduplication records remain available, and that the effect is inside the consumer's local transaction. They do not prove exactly-once behavior for an external email, payment or file write.

The distinction between attempt and event matters in monitoring. Comparing raw broker deliveries with outbox rows will report a discrepancy even when the system behaved as designed. Compare stable unique identifiers and the intended effect state, while tracking duplicates as a separate operational signal. An unexpected increase in duplicate attempts can reveal relay crashes or acknowledgement problems without implying that business effects were duplicated.

## Make the atomic boundary visible in the schema

A minimal event envelope needs a stable event identifier, aggregate identifier, event type, schema version and payload that expresses the agreed event semantics. Include an aggregate version when consumers require sequence validation. Record business occurrence time separately from the time the database or relay observes the event. A timestamp assigned at transaction start is not automatically the commit time, and a sequence number allocated before commit is not automatically commit order.

For an exercise, place an order update and its outbox insert in one local transaction. Force an error between the two statements and verify that neither is committed. Then commit both and stop the process before any publication code runs. The relay must later discover the committed event. This demonstrates the property the outbox actually provides: the database mutation and the durable intent to publish are atomic within that database. The later broker publication is asynchronous.

A self-contained event snapshot is useful when consumers must know what was true at that transition. An identifier-only notification can also be valid when the contract deliberately tells consumers to fetch the current state. Those are different semantics. Do not enrich a historical event from mutable tables at relay time and then present the result as the original state. Equally, do not copy unnecessary personal or sensitive fields into an indefinitely retained event merely to make it self-contained.

## Ordering needs more than sorting by an auto-increment key

Two concurrent transactions can allocate outbox identifiers in one order and commit in another. A polling relay that sorts by identifier therefore does not automatically reproduce commit order. Multiple relay workers can also publish a later event before an earlier event for the same aggregate, even when SKIP LOCKED prevents them from claiming the identical row simultaneously. Row-level concurrency control protects claims, not the full semantic ordering requirement.

Choose an explicit strategy. A single serialized producer per aggregate can allocate a version under the same transaction that changes the aggregate. Relay work can be partitioned by that aggregate and consumers can check versions. A CDC path can use the source's documented transaction ordering, while preserving the required downstream key mapping. If a consumer receives version 12 before 11, decide whether it can safely replace state, must buffer, or must request a replay. The answer depends on whether events are snapshots or noncommutative changes.

A useful lab opens two database sessions, delays the transaction holding the lower allocated event identifier, and commits the higher identifier first. Observe what the relay publishes. Then run two relay workers with an intentional delay before publishing one event. These experiments expose ordering assumptions that a single-threaded happy-path test misses. Keep the expected aggregate versions in the test assertion rather than relying on log-line timestamps.

## Choose polling or CDC with a recovery plan

Polling can be appropriate for a modest workload and a clear latency target. Its production design needs a claim mechanism, expiry or recovery of abandoned claims, broker confirmation handling and a publication status update. Holding database locks while waiting on the broker simplifies some races but increases transaction duration and contention. Releasing locks before publication requires a durable claim protocol. Neither choice eliminates the publish-before-mark crash window.

CDC avoids repeated scans for new outbox rows, but it still consumes database resources and requires durable connector offsets, retention management and failure recovery. A disconnected PostgreSQL logical replication slot can retain WAL and relevant catalog state. Logical decoding can resend recent changes after a crash. The connector and consumer must handle that behavior. Treat the source log position and the broker position as distinct checkpoints, and rehearse recovery when either side is temporarily unavailable.

Monitor oldest unpublished age, pending count, attempts per event, publication failures and end-to-end consumer freshness. For CDC, include retained WAL and connector position. A low pending count can be misleading if the relay marks events before durable acceptance or if a downstream consumer is stalled. Use a periodic canary event or reconciliation query that verifies the actual required destination state.

## Cleanup and poison-event handling are correctness decisions

Delete or archive only events whose publication state satisfies the chosen recovery and audit policy. A time partition containing one unpublished event cannot be dropped merely because most rows are old. If the relay uses a CDC stream, cleanup must also respect the connector's documented behavior and retention requirements. Coordinate source cleanup, broker retention and consumer deduplication retention so an allowed replay does not arrive after its duplicate protection has expired.

An event that cannot be serialized should become an explicit failed item with its identifier, schema version and error context. If ordering matters, skipping it may prevent later events for the same aggregate from being interpreted safely. Decide whether to pause that aggregate, quarantine the sequence or publish a documented corrective event. A dead-letter label alone does not settle the consistency question.

The acceptance worksheet should enumerate crashes before commit, after commit, before broker acceptance, after acceptance but before marking, and after consumer mutation but before acknowledgement. For each, record the permitted retries and expected final state. Run the tests with duplicate and reordered deliveries and inspect the business records, not just the relay logs. The result is a bounded, explainable delivery contract: atomic intent at the source, retriable transport, and idempotent or reconciled effects at the destination.
