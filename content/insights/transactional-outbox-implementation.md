The transactional outbox is this series' most-referenced supporting actor — the standard answer to the dual-write problem (the service that must update its database *and* publish an event, atomically, when no transaction spans both) — and its diagram is deceptively complete: write the business change and the outgoing message to an `outbox` table in one transaction; a relay reads the table and publishes; downstream consumers dedupe. The diagram is correct. The production version has a half-dozen decisions the diagram doesn't show, and each has a wrong default that surfaces as an incident months later.

## The write side: what goes in the box

The outbox row is a message contract frozen at commit time, and its design inherits the event-governance disciplines: **a unique message ID minted at write** (the idempotency key every downstream dedupe will rely on — generated in the transaction, never by the relay), **the full payload, self-contained** (the relay must not re-query the business tables to enrich — the row it reads may be older than current state, and the join-at-publish reintroduces exactly the read-your-own-write races the pattern exists to kill; snapshot what the event needs at commit, per the events-carry-state principle), **event type and schema version as first-class columns** (the registry-compatibility disciplines apply to outbox payloads fully — this table is a message bus wearing a schema), **the aggregate/entity ID as an explicit column** (ordering's foundation, below), and **occurred-at as event time** (the two-clocks honesty: commit time and business time are both recorded, because the consumers' watermark logic will eventually ask).

The write discipline that keeps the pattern honest: the outbox insert happens **in the same transaction as the business change, always, enforced structurally** — a repository/domain-event layer that collects events during the unit of work and flushes them with it (the hexagonal seam doing the work), never an application convention ("remember to also insert the event") that decays into the exact dual-write gap the pattern was bought to close.

## The relay: the component with all the sharp edges

The relay's job — table to broker, reliably — decomposes into the decisions that matter:

**Polling versus CDC.** The polling relay (SELECT unpublished ORDER BY id LIMIT n, publish, mark) is simple, portable, and correct — with the `FOR UPDATE SKIP LOCKED` idiom enabling competing relay workers safely (the job-queue pattern, verbatim) — at the cost of poll-interval latency and steady read load. The CDC relay (the log-tailing tier reading outbox inserts from the WAL — the Debezium-outbox integration productizes exactly this) delivers lower latency and zero query load, at the price of the CDC platform's operational surface (the replication-slot vigilance from CDC practice). The honest default: polling for modest volumes and simpler estates (its latency floor — sub-second at reasonable intervals — satisfies most integration needs); CDC where the outbox is high-volume or the platform already runs the rails.

**Delivery semantics: at-least-once, embraced.** The relay *will* republish (the crash between publish and mark-published is the designed-for case), so exactly-once leaves the vocabulary: the message ID plus consumer-side dedup (the inbox-table discipline) is the contract, and the relay's job is *never losing* rather than never duplicating. The corollary that surprises: **mark-as-published is itself a dual write** (publish to broker, then update the table — a crash between them re-sends), which is fine *because* the ID makes re-sends harmless; relays that try to be clever here (transactional marks against the broker) buy complexity the consumer-side dedup already paid for.

**Ordering: per aggregate, not global.** The guarantee consumers actually need is "events for order 123 arrive in commit order," delivered by publishing with the aggregate ID as the partition key (the per-key ordering from messaging practice) and relaying in commit order (the sequential ID or the log's own order). Global ordering across aggregates is neither promised nor needed — and relay parallelism should shard *by aggregate* (workers own key ranges) rather than by arbitrary batch, or the per-aggregate guarantee quietly breaks under the concurrency that was supposed to be safe.

**Table hygiene: the outbox is a queue wearing a table.** Unmanaged, it grows forever and its polling query degrades (the unbounded-table pathology); the disciplines: published rows deleted (or moved to an archive per the audit-retention needs) on an aggressive schedule, the partition-by-time trick where volume justifies (drop old partitions instead of DELETE churn — the vacuum-pressure mercy for the MVCC engines), and the *unpublished backlog* as the vital sign: *outbox lag* — oldest-unpublished age and backlog depth — alarmed with the absence-detection seriousness of any pipeline, because a stalled relay is silent data divergence in progress: the database moved on, the world didn't hear, and every minute widens the reconciliation.

The monitoring rim completes it: end-to-end publish latency (commit-to-broker, the SLO consumers design against per the staleness-budget honesty), relay error taxonomy (poison messages — the row that fails serialization forever — diverted to a dead-letter state with alerting rather than wedging the stream, per the poison-pill patterns), and the periodic reconciliation count (outbox-published versus broker-received over a window — the trust-but-verify loop that catches the silent partial failure every at-least-once pipe eventually manufactures).

The closing calibration: the outbox is the rare pattern that's both genuinely simple and genuinely subtle — one table, one relay, and a handful of decisions (self-contained payloads, structural writes, per-aggregate ordering, aggressive cleanup, lag alarms) that separate the implementations that quietly carry a company's integration traffic from the ones that generate the "events stopped flowing Tuesday, nobody noticed until Friday" incident. It earns its ubiquity in this series honestly: it's the smallest correct answer to distributed systems' oldest question — how to tell the truth *and* tell someone about it, atomically — and like most smallest-correct answers, the correctness lives in the details the diagram leaves out.
