Compression settings are among the most-copied, least-examined defaults in infrastructure: the web tier gzips because the sample config did, Kafka runs whatever the producer default was, the data lake writes snappy-compressed Parquet because the framework chose, and nobody has measured any of it since. Meanwhile the stakes quietly compounded — egress bills priced per byte, storage tiers priced per GB-month, pipelines whose throughput is bounded by network, and CPU that's either abundant (making heavier compression free money) or the bottleneck (making it a self-inflicted wound). Compression is a *placement-specific optimization with a three-axis trade* — ratio, compression speed, decompression speed — and an afternoon of deliberate choice routinely beats years of defaults.

## What to measure

**Bytes saved per CPU-second.** Compress the same 500 MB corpus at several levels. If an output is 150 MB and encoding took 7 CPU-seconds, it saved 50 MB per CPU-second. Add decode time and end-to-end latency; ratios across different input corpora are rarely comparable.

## The landscape: four names cover almost everything

The modern shortlist collapsed nicely: **gzip/zlib** — the universal legacy: moderate ratio, moderate speed, supported by everything since the 90s; its remaining role is *compatibility floor*, because it wins on no other axis. **zstd** — the modern default, full stop: better ratios than gzip *and* several times faster at both ends, with a wide level dial (fast levels rivaling lz4, high levels approaching archival ratios) that makes it the one-algorithm answer for most storage, streaming, and internal-transfer jobs; its ecosystem support (Kafka, Parquet/ORC, HTTP via `Content-Encoding: zstd` in modern clients, package managers, filesystems) crossed the everywhere threshold years ago. **lz4** — the speed specialist: modest ratios at gigabytes-per-second per core, for the paths where compression must be nearly invisible — in-memory caches, RocksDB-class storage engine internals, real-time streams where microseconds count. **Brotli** — the web specialist: best-in-class ratios for text at slow compression speeds, which is exactly right for *precompressed static assets* (compress once at build time at maximum level, serve a million times — the asymmetry that defines the web tier) and wrong for dynamic responses at high levels (the classic misconfiguration: Brotli-11 on the fly, burning CPU to save bytes the user never notices; dynamic content wants Brotli-4-ish or zstd). Everything else — snappy (lz4's approximate peer, everywhere in older big-data defaults), xz/lzma (max ratio, painful speed — cold archives only) — is a variation on these four's trade-offs.

Start with zstd for a throughput-versus-size comparison, LZ4 for latency-sensitive decompression, Brotli for precompressed web assets, and gzip for older consumers. Benchmark on the actual corpus before setting a default.

## Placement: the same trade, five different answers

**The web tier** splits by asset lifecycle: static assets precompressed at build (Brotli max + gzip fallback, served by content negotiation — CPU cost paid once, per the build-vs-serve asymmetry), dynamic API responses compressed on the fly at moderate levels (with a size floor — compressing 200-byte payloads wastes CPU and can *grow* them — and the security footnote: compression plus attacker-controlled-content plus secrets in the same response enabled the BREACH-class attacks; secrets and reflected input shouldn't share compressed responses). The measurement lens is the web-vitals one: bytes saved matter in proportion to the user's bandwidth, which is why mobile-heavy audiences repay compression attention most.

**Streaming and messaging**: compression batches beautifully — Kafka compresses per record-batch, so producer batching configuration *is* compression configuration (bigger batches, better ratios — the throughput tuning and the compression tuning are one knob wearing two names). zstd as default, lz4 where producer CPU is precious; the payoff is tripled — network, broker disk, *and* replication traffic all shrink together, which in cloud terms means the compression setting is a cross-AZ-traffic line item.

**Storage and analytics**: columnar formats (Parquet/ORC) compress per column-chunk, where encoding and compression interact — sorted, low-cardinality columns compress dramatically better, so *data layout choices are compression choices* (the sort-order decision in the lakehouse quietly moves storage bills by multiples). zstd has displaced snappy as the modern default here; higher levels for cold zones, faster levels for hot, per the tiering economics. For backups and archives, the calculus adds restore-time honesty: the maximum-ratio archive that takes hours to decompress is a recovery-time decision masquerading as a storage saving — the DR-rehearsal discipline includes timing the decompress.

**Internals and caches**: lz4-class speed for anything in the request path (cache values, storage-engine blocks, RPC payloads at high QPS), where the question isn't "does compression help" but "does it fit in the latency budget" — measured, not assumed, because memory-bandwidth-bound services can *gain* throughput from compression (smaller working set, better cache behavior) while CPU-bound ones lose it.

## Dictionary compression: the underused multiplier

The quiet superpower for the small-payload world: compression algorithms learn redundancy *within* a payload, so small documents (the 2KB JSON event, the API response) compress poorly alone — the redundancy is *across* payloads, not within them. **Dictionary compression** (zstd's first-class feature) fixes exactly this: train a dictionary on a sample of representative payloads, share it between compressor and decompressor, and small-payload ratios improve dramatically (multiples, not percentages, on schema-repetitive JSON). The operational shape: dictionaries are versioned artifacts (train, distribute, reference by ID — schema-registry-adjacent governance, because a lost dictionary is unreadable data), retrained as payload shapes drift. Anywhere millions of small, similar payloads flow — event streams, cache stores, log shipping — dictionaries are the difference between "compression barely helps here" and "compression halved this bill."

## The discipline: measure in your units

Compression benchmarks lie the way all benchmarks lie — on someone else's data. The evaluation that means something runs on *your* payloads at *your* sizes, and reports in decision units: ratio (bytes saved → egress/storage dollars, per the envelope math), compression and decompression throughput per core (→ CPU dollars and latency-budget fit), and the end-to-end effect (did p99 move? did pipeline throughput rise?). Revisit when the inputs change — payload shapes, traffic mix, instance pricing, or algorithm ecosystems (the zstd-everywhere shift stranded a generation of gzip decisions) — which in practice means a lightweight annual review of the estate's five biggest compression surfaces, ranked by bytes moved. It's the least glamorous optimization in this series and among the most reliable: the bytes are already flowing, the algorithms are free, and the difference between the default and the deliberate choice is usually a double-digit percentage of a bill somebody's paying.

## Calculate the break-even point for the actual transfer

Compression earns its place when avoided transfer or storage work is larger than the work introduced by encoding and decoding. Start with a layer diagram. Mark where the body is produced, which hop is billed or slow, where a compressed copy is kept, and which readers must decode it. A service that writes a compressed object once may have to decode it on thousands of reads. An edge serving precompressed static assets can avoid most of the per-request encoding cost. The break-even point changes with placement even when encoding the source file generates the same byte count.

Consider an illustrative 8 MiB transfer that shrinks to 2 MiB. At 32 MiB per second, the payload transfer times by themselves are 250 milliseconds and 62.5 milliseconds. Encoding takes 35 milliseconds and decoding takes 12, so if the stages run serially and those rates hold, the compressed path takes about 110 milliseconds for those three steps. At 256 MiB per second the uncompressed transfer takes 31.25 milliseconds, while the encoded transfer takes about 7.8 milliseconds plus 47 milliseconds of compute. The same codec may help the slower hop and hurt the faster hop. Header time, overlap, congestion and request setup are omitted from this example.

A first model at a known link rate is useful even when the server streams the result. Replace serial timing with an experiment when encoding overlaps transfer. Report time to first byte, time to complete the first useful portion, and time for the whole body. A large buffer may maximize the ratio while delivering the first useful data much later. If input arrives slowly, identify whether the codec is waiting for a frame or an upstream has yet to produce enough work to fill the buffer.

In both cases, record CPU time at all the places that perform compression or decompression. Converting seconds into CPU capacity requires the request rate as well as per-request cost. An added 0.8 milliseconds of CPU per request at 2,000 requests per second uses 1.6 CPU-seconds each second before retries and scheduling overhead. That can fit in one estate and be significant in another. Verify with reserved cores and realistic concurrency. Wall-clock time on a quiet workstation cannot tell how much capacity remains when many encoders share a production quota.

## Select a comparison corpus before looking at ratios

Sample from units that the production software actually encodes. An HTTP API often compresses one response at a time, whereas a log collector may compress a batch. Compressing an entire dump as one file measures a larger history than many runtimes can access. Divide samples by body size, content class, and recurrence. Include already compressed assets, high-entropy payloads, and responses with changing identifiers. Retain the size and traffic distribution so the result applies to a declared workload rather than to a favorite fixture.

Use the same input order, negotiated content encoding, compression level, dictionary and decoder version across repeats. Compare bytes emitted after framing, not only the codec's compressed data field. Check memory as well as CPU when choosing window settings. The [Zstandard manual](https://facebook.github.io/zstd/zstd_manual.html) describes compression parameters, dictionaries and decoder behavior. For a compatibility test, preserve the exact minimum version and architecture among readers. A new producer that emits output an existing reader cannot decode has introduced a format upgrade, whatever the throughput result.

Keep benchmark outputs in a lossless comparison report. One row per corpus and configuration can show input bytes, output bytes, encoder and decoder CPU, first-byte time, request tail time, and peak memory. Keep an uncertainty or spread column when repeat runs vary. Report changes in decoded output as failures even if compression appears to save all the expected bytes. Round ratios after calculations and include input and output byte totals so reviewers can reproduce them.

## Make web negotiation part of the correctness test

For HTTP traffic, a successful compression test includes the cache path. Request an asset through the real edge configuration with client profiles using Brotli, gzip and identity encoding where supported. Confirm each payload's encoding metadata, verify its decoded contents, and check that one client's cached response cannot be served to a client that requested incompatible encodings. An origin configured to send alternate representations and negotiate on a request header must account for selection when reusing a response. See [RFC 9110's content negotiation and Vary semantics](https://www.rfc-editor.org/rfc/rfc9110#section-12.5).

Store variant metadata beside the bytes. A static asset build may produce multiple representations with different byte lengths. Verify the server selects lengths and validators consistent with the representation it gives the client. Test after deploy and after cache revalidation as well as on a cold request. Report expected identity fallbacks separately from incorrectly skipped compression. A change that increases compatibility without improving data reduction can still be the correct release.

Check unusual paths such as an empty response, a tiny payload, a large streamed payload, and content whose size is only known after the producer starts. Exclude responses that policy requires to stay uncompressed. Keep decode errors and time to useful output visible next to aggregate bytes saved, since aggregate success can hide one important client class failing entirely.

## Rehearse dictionary transitions and retirement

A trained dictionary becomes data required to recover the bytes it helped compress. In an illustrative system an archive holds data for 60 days and backups can restore records to an older environment. If producers start using dictionary B today, deploy readers that can handle both A and B before any B-tagged records appear. Keep the identifier, bytes, expected checksum and scheme version in a distribution path that recovery tooling can reach independently of the main application. Count decoded records per dictionary to see when migration is safe.

Retire A only after the oldest possible restore no longer needs it or after rewriting data that still references it. A message replay and an object restoration should both be part of verification. Treat missing or inconsistent dictionary metadata as a distinguishable error rather than silently decoding it with the newest version. Keep a tested way to return producers to A while both formats are supported. A small reduction in storage cost rarely justifies a restore path that depends on an unpreserved artifact.

A separate risk is measuring only the happy decode path. Run an isolated reader against truncated frames, a checksum mismatch where the format uses one, and a bounded output whose decoded size exceeds the application's configured limit. Decoder resource policies need explicit values before enabling untrusted client inputs. Record full decode success, controlled rejection, and how quickly memory is released. When testing historical archives, read a representative old file through the same restore software and verify the decoded inventory. Archive verification should test that the system rebuilds useful records from the bytes rather than merely reading files with no codec error.
