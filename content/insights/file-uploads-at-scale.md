File upload is the feature with the widest gap between how casually it's added ("just accept a multipart POST") and how much surface it actually opens: it's the one place your system ingests *arbitrary attacker-controlled bytes by design*, it couples your request path to the slowest clients on the worst networks, and its outputs get served back to other users' browsers — which makes a naive upload feature simultaneously a DoS vector, a malware distribution channel, and a stored-XSS factory. The mature architecture is well-converged and worth having in your head *before* the sprint that adds it.

## The transfer architecture: get out of the data path

The foundational move: **application servers should broker uploads, not carry them.** The proxied-upload pattern (client → your API → storage) puts every large transfer on your request path — worker threads/connections held for the duration of slow mobile uploads (the queueing math says a few hundred slow uploaders can starve an interactive fleet), memory/disk staging pressure, and your ingress bandwidth as the ceiling. The standard answer is **direct-to-storage with presigned URLs**: the client asks your API for permission; the API authorizes (the business-level checks — quota, entitlement, content-type intent), records a pending-upload row, and returns a short-lived, tightly-scoped presigned URL (specific key, size cap via policy, expiry in minutes — the time-boxed capability pattern from object-storage practice); the client uploads straight to the bucket; completion is signaled by client callback *and verified server-side* (never trust the callback alone — the event-notification from storage, or a verification check, is the truth; the client that says "done" for an object that doesn't exist is routine). Your servers touch metadata, never payload — the thin-control-plane/fat-data-plane split that every scalable transfer system converges on.

**Resumability** is the second-order requirement mobile reality imposes: multi-hundred-MB uploads over flaky networks need chunked, restartable transfer — multipart upload APIs (per-part presigning, parts retried independently and in parallel — which also raises throughput per the parallel-ranged-transfer physics) or the tus-class resumable protocols where you control both ends. The operational footnote from storage practice applies doubly here: **incomplete multipart uploads accrue invisibly** — the abandoned-upload lifecycle rule is mandatory hygiene, not optional cleanup.

## The gauntlet: no file is trusted until processed

Everything that arrives goes through a validation-and-processing pipeline *before* it's referenced as real, and each stage exists because of a specific attack: **verify the actual type** (magic-bytes/content sniffing, never the client's Content-Type or extension — the polyglot file that's simultaneously a valid image and valid HTML/script is a classic serving-layer exploit; allowlist types, reject ambiguity), **enforce limits early** (size caps at the presigned-policy layer and dimension/complexity caps at processing — decompression bombs, gigapixel images, and deeply-nested archives are resource-exhaustion attacks wearing file extensions; parsers get sandboxed, resource-limited workers, because image/document parsing libraries have the CVE history to earn container isolation), **scan for malware** (the async-scanning tier for anything re-downloadable by other users — quarantine-then-release semantics: the object is unavailable until scanned, per the pending→clean state machine), **strip and re-encode where the product allows** (re-encoding images destroys embedded payloads and — the privacy dividend — strips EXIF location metadata that users didn't know they were sharing, per the data-minimization instincts; the transform *is* the sanitizer), and **process asynchronously** (the pipeline — scan, thumbnail, transcode, index — runs on queues per the batch-and-messaging disciplines: idempotent per file, dead-lettering the poison files, with the upload's user-visible status tracking pipeline state honestly).

## Serving: the half everyone forgets

Stored files come back out, and the serving layer has its own attack surface: **never serve user uploads from your application origin** (the polyglot-file XSS above executes in *your* origin's context if served there — the dedicated user-content domain, a separate origin entirely, is the isolation move the major platforms all made; cookies and page authority don't reach it), **force the safe headers** (`Content-Disposition: attachment` for anything not explicitly safe-to-inline, `X-Content-Type-Options: nosniff`, and Content-Type set from your *verified* type, not stored client claims), **authorize per fetch** (private files behind short-lived presigned GET URLs or an authorizing proxy — the public-bucket incident genre from storage practice is disproportionately user-upload buckets; access control at share-link granularity is a product feature with a security implementation), and **CDN with the private-origin discipline** (cached delivery for the public tier, per the caching rules — with cache keys and authorization designed together, because a CDN-cached private file is the caching-layer breach from HTTP practice).

The lifecycle rim completes it: ownership and retention per file class (the privacy-engineering deletion rails reach into upload storage — user deletion means object deletion plus CDN purge plus thumbnail-and-derivative cleanup, which is only tractable if derivatives were keyed traceably to sources), storage tiering by access pattern (the object-lifecycle economics — user uploads are textbook hot-then-cold data), and per-tenant quota metering (the usage-metering machinery, pointed at bytes). The design-review checklist compresses to five questions: does payload bypass your servers, is type verified from bytes, what happens to a malicious file at each stage, from what origin with what headers does it come back out, and who deletes it when. The feature ships in a sprint either way — the difference is whether those answers were designed or will be discovered, and the discovery mechanism for upload features is never a unit test. It's a disclosure.
