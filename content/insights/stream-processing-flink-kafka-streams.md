Batch processing has a comforting shape: the data arrives, the job runs, the answer exists. Stream processing removes the comfort by removing the end — the data never stops, so "the answer" becomes a moving computation over an unbounded input, and an entire batch-era mental model quietly breaks: there is no "all the data," no "job finished," no natural moment when the count is final. Teams that adopt streaming infrastructure while keeping batch mental models produce the field's characteristic bugs — counts that change after being reported, aggregations missing the events that arrived late, pipelines that silently double-count after failures. The fixes are conceptual first, tooling second.

## The concepts that do the heavy lifting

**Event time versus processing time** is the foundational split: *when the thing happened* versus *when your system saw it* — and they diverge constantly (mobile clients batching uploads, network delays, replayed backfills). Any computation whose meaning references the real world — "orders per hour," "sessions per user" — must be computed in **event time**, or its answers change depending on infrastructure weather. Which creates the problem event time can't dodge: how long do you wait for stragglers before declaring an hour's window closed? That answer is the **watermark** — the stream's own moving assertion that "events earlier than T have (probably) all arrived" — and it's a *policy you choose*, trading latency against completeness: aggressive watermarks report fast and miss late events; generous ones are complete and slow. Mature pipelines make the trade explicit and handle the leftovers deliberately (late-event side-outputs, window retractions/updates downstream — the "count was 1,042, now it's 1,047" reality that consuming systems must be designed to absorb, which is an *interface contract*, not an implementation detail).

**State is what makes streaming hard** — and useful. The interesting computations (joins across streams, sessionization, running aggregates, deduplication, the fraud model's per-card history) all require remembering things per key across events, which means the processor is a *stateful distributed system*: state must be partitioned (by key, riding the Kafka-partition discipline), persisted (local stores with changelog/checkpoint backup), and — the crux — **restored consistently after failure**. This is where "exactly-once" earns its honest formulation: not exactly-once *delivery* (impossible, per the idempotency truths) but **exactly-once *state effects*** — checkpointing input positions and state snapshots atomically (Flink's coordinated checkpoints, Kafka Streams' transactional commits), so a crash rewinds to a consistent point and replays without double-counting *within the pipeline*. The fine print that survives all marketing: outputs to *external* systems still need transactional sinks or idempotent writes — the boundary discipline never goes away; the framework just handles the interior.

## The tooling decision, by workload shape

**Kafka Streams** (and its lighter functional kin) is a *library, not a cluster*: your stream job is a normal JVM application — deployed, scaled, and operated like any service (the same CI/CD, the same Kubernetes), with state in embedded stores backed by Kafka changelogs. It's the right default when the sources and sinks are Kafka, the team already operates services well, and the topology is application-shaped (enrich, join, aggregate, emit). Its constraints: JVM-only, Kafka-only, and coordination features (large state rebalancing, complex event-time machinery) that are workable but not its center of gravity.

**Flink** is a *platform*: a cluster (or managed service) running jobs with the field's most complete event-time/watermark/state machinery, genuinely large state (terabytes, with incremental checkpoints), sophisticated windowing/CEP, and SQL as a first-class interface. It earns its operational weight when the workloads are pipeline-shaped and demanding — multi-stream joins at scale, complex event-time correctness, state beyond what embedded stores comfortably hold — or when a platform team serves many streaming use cases centrally. The managed offerings have substantially blunted the "Flink ops are hard" objection, per the usual buy-the-control-plane logic.

**Streaming SQL engines** (Flink SQL, the materialized-view engines, the streaming-database products) are the rising third option: declare the computation, let the engine maintain it incrementally. For the large fraction of streaming needs that are really "keep this aggregation/join current" — dashboards, features, caches — they collapse enormous implementation surface, and the honest modern evaluation starts here: *can this be a maintained view?* before *should this be a coded topology?*

(And the perennial pragmatic contender: **micro-batch** — Spark Structured Streaming and friends — remains a legitimate answer when minutes-level latency suffices and the team's world is already Spark; the "real streaming vs micro-batch" purity debate matters far less than the latency requirement, which should be written down before any of this is chosen.)

## The operational reality: jobs that never finish

A streaming job is a service with a database inside, and its operations follow: **lag is the vital sign** (consumer lag per partition — the streaming SLO, alarmed by burn-rate logic like any other), **checkpoint health is the safety net's pulse** (duration and failure alarms, because a job whose checkpoints silently fail is accumulating an unbounded replay), **state size is capacity planning** (unbounded keys mean unbounded state — TTLs and windowing as policy, per the retention disciplines), **backpressure is the design question, not the incident** (when input outruns processing, something must give — buffer, shed, or scale; choosing at design time beats discovering at 2 AM), and **schema evolution rides the same governance as every stream** (the message-contract discipline, doubly binding because state *outlives* deployments — the job restored from checkpoint must read its own year-old state under the new code, which is a versioning discipline teams discover exactly once). And the **replay/backfill path is the superpower to preserve**: the log-plus-deterministic-job combination means bugs can be fixed by reprocessing history — if event-time logic is honest, sinks are idempotent, and topics retain enough (the tiered-storage economics making "enough" generous). Pipelines designed for replay convert data bugs from incidents into batch jobs — the same rebuildability principle as every derived-store pattern, and the reason the discipline pays for itself the first bad week.

The compact placement rule: **materialized-view engines for "keep this current," Kafka Streams for Kafka-native application logic, Flink for heavy multi-stream event-time work, micro-batch when minutes suffice** — with event-time correctness, exactly-once state semantics, idempotent sinks, and replay-ability as the non-negotiables whatever runs underneath. The unbounded world is now the default shape of enterprise data; the teams that think in watermarks and state — rather than in jobs that finish — are the ones whose numbers stay true while the data keeps arriving.
