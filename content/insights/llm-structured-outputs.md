Every LLM integration crosses the same maturity threshold: the demo where the model returns a nice JSON blob, and the production incident where — an occasional request — it returns the blob wrapped in markdown fences, or with a trailing comma, or with a helpful preamble ("Here's the extraction you requested:"), or with a field renamed by paraphrase, and the pipeline downstream throws on parse. Structured output — getting *schema-conformant, machine-consumable* data from a probabilistic text generator — is the unglamorous discipline that converts LLM capabilities into system components, and its toolkit has matured enough to have right answers.

## The mechanism ladder: instructions, repair and decoding constraints

The approaches rank by how much conformance they *guarantee* versus request: **prompt-and-hope** (schema described in the prompt, model asked to comply — a configuration whose conformance must be measured on the actual workload), **prompt-parse-repair** (the pragmatic middle: lenient extraction — strip fences and preambles, tolerant JSON parsing — then schema validation, then a *repair loop*: the validation errors fed back to the model for one correction pass — a correction attempt whose success rate must be measured at the cost of a second call's latency and spend), and **constrained decoding** (the production tier: the model's token generation *masked against a grammar* compiled from your schema — permitted tokens are restricted by the supported grammar, although incomplete responses, refusals and implementation failures still require handling — the mechanism behind the providers' native structured-output/JSON-schema modes and the open-source equivalents for self-hosted serving). The selection logic: constrained decoding wherever the provider or serving stack offers it against your schema features (the JSON-Schema subset supported varies — the compatibility check is part of vendor evaluation now), with the parse-repair ladder as the fallback tier and *always* as the validation backstop — because supported constrained decoding targets syntax and schema shape, not *semantic* validity (the date that parses but lies, the enum chosen wrong), and the boundary-validation disciplines apply to model output exactly as to any untrusted input: the LLM is an external system whose responses get schema-validated at ingress, full stop.

## Schema design for a probabilistic author

The schema is also a prompt — the model reads field names and structure as instructions — which adds ergonomic rules atop the classical contract disciplines: **names that self-describe** (`customer_sentiment` over `cs_val`; description fields can guide the model but are not validation constraints — invest in them like the tool-description discipline, because they are the same discipline), **enums and constraints over free text wherever the domain is closed** (every free-string field is a paraphrase opportunity; every enum is a decision you've pre-made — and a correctly implemented decoder can constrain completed output to supported enums, while refusals, truncation and implementation errors still need handling; an allowed enum value can nevertheless be the wrong classification), **structure that matches reasoning order** (models fill fields sequentially: field order may affect task performance and should be evaluated; request concise evidence references when useful rather than assuming a generated rationale faithfully explains the decision), **optionality made explicit and escapes provided** (requiring a value without an absence representation can encourage unsupported guesses or cause a failed response — nullable fields with "null when not present" instructions, and an explicit `confidence`/`not_found` channel, are the design that makes absence representable — the same lesson every data model learns about pretending completeness), and **flatness over cleverness** (deeply nested optional structures multiply the conformance surface; the flat-with-post-processing shape is the pragmatic winner — the KISS instinct, with token-budget economics attached).

## The production rim: the parts the demo skips

The operational disciplines once structured output is load-bearing: **versioned schemas with the full contract treatment** (the schema is an interface consumed by both the model and your pipeline — changes ride the compatibility rules, and *model version pins interact with schema behavior*: the provider's model upgrade that subtly changes field-filling behavior is a dependency-upgrade event needing the eval gate, per every AI-change discipline), **evaluation on semantic correctness, not just parse rate** (the golden-set suite asserting extracted values against ground truth — parse-success dashboards showing 100% while extraction quality degrades is the silent-wrongness genre, in structured clothing), **failure-path design** (the repair loop has a budget; past it, the item routes to the dead-letter/human-review lane per the pipeline disciplines — a structured-output system without a "model couldn't comply" path has decided to either drop or hallucinate its hard cases, silently), **telemetry per field** (repair-rate and null-rate by field name is the diagnostic that finds the ambiguous schema element — the field that triggers half the repairs is a design bug announcing itself), and **cost-latency honesty** (constrained decoding overhead depends on implementation and schema; repair loops add inference work on the failure tail; and schema token-weight — the verbose deeply-described schema resent on every call — is a prefix-caching and budget line item per the context-engineering economics).

The closing frame: structured output is where the "LLM as component" claim gets tested, and the passing grade is the same one every component earns — *its failure modes are enumerated, bounded, and handled*. Constrain the decoding where possible, validate at the boundary always, design schemas as the prompts they are, give absence a representation, budget the repair tail, and eval the semantics — and the probabilistic text generator becomes what the pipeline needs it to be: a function with a signature, whose occasional refusals arrive as typed errors instead of parse exceptions at 2 AM.

## A concrete extraction contract

Consider a hypothetical accounts-payable intake tool. It reads a document and proposes an invoice number, currency, invoice date, line items and total. It does not approve payment. That separation determines the schema: extraction fields describe evidence, while the payment service independently applies authorization and accounting rules. A model-generated field named `approved` must never become an authorization decision simply because it has a Boolean type.

Represent missing information explicitly. An absent purchase-order number should be null with a short status such as `not_found`, rather than an invented identifier or an empty string that downstream code interprets inconsistently. Use a separate status for illegible evidence; absence and unreadability require different follow-up. Keep an original-document reference and page number so a reviewer can inspect the relevant location. A quoted evidence span may be helpful, but it too needs verification against the source.

Money requires a documented representation. For a single currency with two decimal places, an integer count of minor units can avoid binary floating-point surprises. A system supporting currencies with different minor-unit conventions needs currency-specific rules instead of multiplying everything by 100. Keep the original extracted amount when normalization changes its representation. A total that passes a numeric constraint can still be in the wrong currency or refer to a previous balance rather than the invoice amount.

The validation stages should report distinct outcomes: transport completed; response completed rather than truncated or refused; JSON parsed; schema matched; field meanings checked; business invariants checked; and human approval, when required, completed. A refusal is an application outcome, not malformed invoice data. Catching every exception and returning an empty invoice turns a visible failure into silent data loss.

## Worked example: separate shape from correctness

In a synthetic evaluation of 200 invoices, an unconstrained prompting configuration returns 190 schema-valid responses. A second configuration returns 198 schema-valid responses. Reviewers then compare the complete invoice records with independently prepared reference records: 174 are fully correct in the first configuration and 180 in the second. The chart reports four counts: 190 and 198 for schema validity, 174 and 180 for semantic correctness. These are overlapping measures on the same 200 inputs, not four disjoint groups.

Schema validity rises from 95% to 99%, a four-percentage-point improvement. Complete-record correctness rises from 87% to 90%, a three-percentage-point improvement. Among schema-valid responses, correctness is 174/190, approximately 91.6%, versus 180/198, approximately 90.9%. That conditional proportion falls slightly even while more invoices become usable overall. Reporting only the conditional figure would hide the improved coverage; reporting only parse success would hide 18 structurally valid but incorrect records in the second configuration.

These numbers are hypothetical, not a provider comparison. Hold the model, document corpus and acceptance rubric fixed when testing the decoding mechanism itself. If the model also changes, describe the result as a configuration comparison. Include scanned documents, multi-page invoices, missing fields and unfamiliar vendors. Report subgroup counts rather than assuming an overall result transfers to the rare documents that create most accounting risk.

## Repair without turning errors into guesses

A repair request can fix representation errors, but it should not invent facts to satisfy a schema. If the model supplied `31 February`, replacing it with the nearest plausible date is an unacceptable repair unless the business explicitly asks for an inferred date and records that inference separately. A safer response is a typed validation failure with the source document retained for review.

Bound repair by attempts, total elapsed time and total tokens. A slow repair is still slow even if its JSON is perfect. Distinguish retrying an unavailable provider from asking a completed generation to revise a field. Store attempt identifiers so support staff can determine which response was actually accepted. Avoid sending the entire document into exception logs; document identifiers and validation categories often provide enough operational detail.

Schema evolution needs consumer tests. Adding an enum value can break consumers with exhaustive branching. Adding a required property can reject old queued messages. A migration may need parallel readers, an explicit schema version, and a cutoff after which old records receive a controlled transformation. Do not assume a field description is a constraint: JSON Schema annotations and validation keywords have different jobs, and even date-format enforcement depends on validator configuration.

## A small validation lab

Create 12 invented invoice records: four ordinary, two missing purchase-order numbers, two with inconsistent totals, two using ambiguous dates, one truncated response and one explicit refusal. Save both the proposed extraction and the expected disposition: accept, review or retry. No real financial document is needed for this exercise.

First test the validator with hand-written JSON so that model variability cannot conceal a validator bug. Assert that the inconsistent totals fail the business rule even when every property has the correct type. Assert that a valid null is distinguishable from a missing required property. Then run the same documents through the model and compare field-level and record-level outcomes. Keep an unmodified set for later regression testing instead of repeatedly optimizing against all 12 examples.

The worksheet should contain document identifier, schema version, response status, parse result, schema errors, semantic errors, final disposition and elapsed time. Review one failure from each category with the engineer responsible for the downstream consumer. Their question is not simply whether the payload can be decoded; it is whether the consumer can act safely without reconstructing missing context.

Before release, simulate a schema change while old messages remain in the queue. Verify that retries do not create duplicate business records and that a reviewer can recover the source evidence. These operational exercises test the part of structured output that constrained generation cannot guarantee: a reliable interface between uncertain extraction and a consequential application.
