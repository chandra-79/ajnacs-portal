API teams lavish design attention on their HTTP surface — resource modeling, error contracts, pagination semantics — and then ship the layer through which most consumers actually experience all of it as an afterthought: the SDK, generated on a Friday or hand-grown by whoever complained loudest. The inversion is costly because the SDK *is* the interface for the majority of integrations, and its quality compounds in both directions: a good client library makes every API design decision — the idempotency keys, the retry semantics, the pagination cursors — *automatic* for consumers who'd otherwise implement them wrong; a bad one converts your careful contract into per-customer folklore and your support queue into a distributed debugging service.

## The design bar: correct by default, idiomatic per language

The SDK's first job is encoding the behaviors your API's reliability model *depends on* consumers having — the ones the docs ask for and integrators skip: **retries with exponential backoff and jitter, honoring Retry-After, budget-capped** (the retry-storm physics say your SDK's defaults *are* your load profile during incidents — shipping the correct behavior is self-defense), **idempotency keys generated automatically** for the operations that need them (the double-charge prevention from idempotency practice shouldn't depend on the integrator reading that chapter — the SDK mints the key per logical operation and reuses it across its own retries), **pagination as iteration** (the cursor mechanics wrapped in the language's native iterator/async-iterator idiom — consumers write `for order in client.orders.list()` and the SDK walks cursors, respects rate headers, and stops correctly; hand-rolled pagination loops are where the skip-and-duplicate bugs live), **timeouts with sane defaults and per-call overrides** (the timeout-hierarchy discipline, pre-wired), **auth lifecycle handled** (token refresh, credential rotation hooks — the OAuth machinery from identity practice, invisible), and **typed errors matching the API's taxonomy** (the problem-details contract surfaced as catchable, documented exception types with the retryability flag attached — so client code branches on `RateLimitError` versus `ValidationError` rather than parsing strings).

The second job is *feeling native* per language — the bar that pure generation struggles to clear: naming conventions, error idioms, async models (asyncio-native for Python per the async disciplines, promises in JS, contexts in Go), the packaging norms of each ecosystem (the lockfile-friendly, semver-honest publishing from dependency practice), and type definitions as first-class (the typed-boundary payoff: the SDK's types *are* the API contract in the consumer's IDE — autocomplete is documentation with zero latency, and in the AI era it's also what makes assistants generate correct integration code against your platform, which is quietly becoming a distribution channel: the SDK that models well prompts well).

## The production architecture: generate the skeleton, craft the muscle

The build-versus-generate decision resolved into a hybrid that's now standard practice: **the OpenAPI/contract spec generates the mechanical tier** (models, serialization, endpoint bindings — guaranteeing coverage and contract fidelity, per the docs-from-truth principle: the spec is the source, and drift between API and SDK becomes structurally impossible), while **a handcrafted layer owns the experience tier** (the retry/idempotency/pagination behaviors above, the ergonomic entry points, the per-language idiom) — with modern SDK-generation platforms (the Fern/Stainless-class tooling that the major API companies converged on) productizing exactly this split. The operational corollaries: the spec becomes load-bearing beyond docs (its accuracy is now a release gate — the contract-testing disciplines apply), SDK releases ride CI from spec changes (new endpoint merged → SDKs regenerated, tested, published across languages — the multi-repo automation from polyrepo practice), and the language matrix is a *commitment*, chosen deliberately (each language is a permanent maintenance surface with its own ecosystem cadence — the tiering answer: first-class languages with full experience layers, generated-only tier for the long tail, and honesty in the docs about which is which).

## The contract: versioning, telemetry, and support reality

The SDK inherits every API-evolution discipline with extra surfaces: **semver honesty** (breaking the SDK's types or behavior is a major version even when the wire API didn't change — consumers pin your library, not your endpoints), **deprecation with runtime signals** (the deprecated method that warns with a migration pointer beats the changelog nobody reads — the usage-tracking dividend: SDK telemetry showing version and feature adoption is how you know when the old major can actually die, per the deprecation-evidence practice), **a support-window policy published** (which majors get security patches, for how long — the enterprise procurement question that arrives with the first big customer), and **the transitive-dependency diet** (every dependency your SDK carries is a version-conflict lottery ticket in the consumer's build — the mature SDKs vendor or minimize aggressively, because being the library that broke someone's unrelated upgrade is how you get ripped out). And instrument the funnel like the product surface it is: time-to-first-successful-call *through the SDK* (the docs-metric from developer-experience practice, now measured at the layer most integrations actually use), error rates by SDK version (the client-side telemetry — with consent and privacy discipline — that turns "integrations are struggling" from support anecdote into dashboard), and the issues/discussions channel staffed as the developer-experience front line it is.

The closing reframe: an API without a serious SDK strategy is a specification hoping its consumers are diligent — and the whole arc of this series says systems that depend on distributed diligence lose to systems that encode the behavior. The SDK is where your platform's reliability disciplines — retries, idempotency, pagination, timeouts, typed errors — stop being documentation and become defaults, shipped to every integration, in every language, maintained like the product it actually is. The endpoints are the contract; the SDK is the handshake — and handshakes are what integrations remember.
