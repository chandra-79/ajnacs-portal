Test permitted and denied paths in a clinical-software lab

#Hypothetical learning need

A fictional clinical-software team wants to replace broad network reachability with an explicit dependency policy. The proposed training uses a synthetic scheduling application, fake records and an isolated cluster. It does not access clinical systems or certify regulatory compliance. Participants begin by identifying DNS, application, database and observability paths and explaining which component initiates each connection.

#Technical design

The laboratory contains a frontend, API, database simulator and telemetry receiver. Learners write an allowed-path matrix before applying policy. They then introduce a default-deny posture and add only the required paths. The Kubernetes NetworkPolicy documentation is used to verify semantics and the selected network plugin's support. The existence of a policy object is not accepted as proof of enforcement.

The instructor includes a missing DNS allowance, an unintended namespace selector and a client trying to reach an unrelated service. Pairs predict the result, run a controlled connectivity check and inspect application behaviour. The exercise distinguishes transport reachability from application authorization: a permitted TCP connection does not mean the caller is entitled to every record.

#Synthetic test matrix and chart

The invented matrix has 12 checks: five required paths that must succeed and seven prohibited paths that must fail. A deliberately flawed initial policy produces nine correct outcomes and three incorrect outcomes. The corrected capstone is expected to produce 12 correct outcomes. The chart compares nine and 12 verified outcomes out of the same defined matrix. These values are teaching fixtures, not a measured security posture of a healthcare organisation.

The evidence includes source identity, destination, protocol, expected result, observed result and the policy revision. Tests use controlled endpoints and do not scan external networks. A successful denial is reported as an expected result rather than an application outage. The team also checks the normal user journey so an over-restrictive policy cannot pass by blocking everything.

#Acceptance and lifecycle

Acceptance requires all required and prohibited path checks to match expectations, with a clear explanation of selectors and namespace boundaries. Learners must restore a known policy revision after an intentionally broken change and verify that the application recovers. They identify remaining controls outside NetworkPolicy, including API authorization, secret access and ingress configuration.

Lab identities cannot modify production networking. Synthetic records and diagnostic logs have fixed retention, and cleanup removes policy objects, namespaces and external resources. Handover includes the dependency matrix, test runner, rollback procedure and plugin-specific limitations. A later transfer task introduces a new telemetry destination and a namespace-label change, requiring participants to review policy meaning rather than copy a permissive rule to make traffic work.
