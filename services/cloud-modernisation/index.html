#Start with the workload decision

Cloud modernisation should improve a named business capability, operating constraint, or delivery problem. Moving infrastructure is a possible intervention, not the objective itself. A proposed engagement begins with one workload and a decision the organisation needs to make: retain the current platform, move it with limited changes, adopt a managed component, replace a capability, or redesign a bounded part. The examples below are hypothetical delivery plans with synthetic numbers. They describe how work could be performed and evaluated; they are not claims about customer engagements or guaranteed results.

The initial charter identifies the sponsor, service owner, users, critical journeys, commercial constraints, and the evidence required to proceed. It also states what remains outside scope. A database migration does not silently include redesigning every application, and an infrastructure assessment does not confer permission to change production. Discovery ends with a documented option comparison and an accountable decision, including the option to retain the workload where a move is not justified.

#Inventory dependencies before choosing a destination

Build an inventory from interviews, configuration, deployment records, traffic evidence, and controlled observation. Record application versions, runtime support, data stores, batch schedules, identity providers, external APIs, file exchanges, certificates, and operational ownership. Trace a small set of real business journeys across those components. A list of virtual machines misses dependencies expressed through shared storage, scheduled jobs, service accounts, and undocumented network rules.

Classify evidence by confidence. An owner saying a database is unused is a hypothesis until retention obligations, scheduled activity, and downstream consumers have been checked. Record observation windows, including month-end or seasonal work that may be absent from a short trace. Maintain an unresolved-dependency register with an owner and a validation step. The migration plan should expose uncertainty instead of converting an incomplete inventory into a confident diagram.

#Agree access and data contracts

Use named, time-bounded access appropriate to the discovery task. Prefer read-only inventory and metrics access initially, with separate approval for changes. Document the accounts, regions, repositories, secrets systems, billing exports, and databases involved. Credentials belong in the organisation's approved secret-management process, not assessment documents or examples. Keep a record of who can authorize temporary access and who verifies its removal at handover.

For data, define classification, permitted locations, retention, deletion, encryption ownership, and the allowed use of production-derived samples. Masking does not automatically make a dataset anonymous. Synthetic fixtures may be more suitable for early tests, while carefully controlled representative data may be needed to reveal encoding, size, or referential-integrity problems. Specify schema versions, identifier meaning, time zones, null handling, and reconciliation rules before building a transfer pipeline.

#Compare architecture options against constraints

Use an architecture decision record for each consequential choice. The record includes alternatives, evidence, expected benefit, new obligations, reversibility, and review triggers. Migration categories such as retain, rehost, replatform, and refactor help describe scope; they do not rank approaches from bad to good. A well-operated modular application may be preferable to several services when independent scaling or ownership does not justify distributed failure modes.

Compare total operating requirements rather than only infrastructure features. A managed database changes patching responsibilities but still needs schema ownership, access control, capacity planning, restore tests, and application compatibility work. Containers can improve packaging consistency while adding orchestration and image-maintenance obligations. A second region can support a recovery design, but replication lag, shared identity dependencies, and failover procedures determine what the design actually achieves.

#Establish measurable acceptance before implementation

Define a small acceptance matrix linking each requirement to a test and an approver. Functional correctness might mean that selected order states, exports, and user permissions behave equivalently. Performance requirements should name the operation, load model, duration, dataset, client location, and percentile calculation. Reliability requirements should distinguish request success from elapsed outage time. A request-based objective cannot be translated into minutes of downtime without assumptions about traffic.

Data acceptance needs more than a row count. Compare totals, keys, relationships, selected field values, and business invariants. Specify how late writes, duplicates, deleted records, and clock differences are handled. Recovery acceptance should state the recovery-time and recovery-point objectives and the actual start and end events used to measure them. An objective is a target; only a controlled rehearsal provides evidence of a particular observed recovery.

#Build a reproducible target foundation

Create the target through reviewed infrastructure definitions wherever the chosen platform supports it. Separate environments, define identity boundaries, establish logging and cost attribution, and document network paths. Use narrowly scoped workload identities rather than long-lived shared credentials where supported. Record platform versions and configuration inputs so another engineer can recreate the environment and explain differences between test and production.

Start with the minimum foundation required by the pilot. A large landing-zone programme can overwhelm a small workload assessment if every possible future feature becomes a prerequisite. Conversely, bypassing identity, logging, or network ownership creates expensive ambiguity later. Make those tradeoffs explicit. The foundation is ready when the pilot can deploy, communicate, emit useful telemetry, obtain required credentials, and be removed through a documented process.

#Move data with a consistency plan

Choose bulk copy, change capture, dual operation, or a maintenance-window transfer according to the data model and tolerated interruption. Each approach introduces different risks. Change capture needs a known starting position and a way to determine catch-up. Dual writes can diverge when one destination succeeds and the other fails. A maintenance window simplifies some consistency problems but requires a realistic estimate of transfer and validation time.

Rehearse the sequence with representative volume before scheduling production. Record throughput distributions and bottlenecks rather than extrapolating from one small file. Verify permissions, indexes, sequences, character encoding, and application semantics after transfer. Keep source and target ownership clear during cutover. If the target accepts writes, returning traffic to the source may require reverse replication or reconciliation; switching DNS alone does not restore consistency.

#Test a bounded pilot

Select a pilot with meaningful dependencies and a recoverable scope. Define traffic limits, test accounts, permitted data, maximum resource consumption, and abort conditions. Exercise normal paths, slow dependencies, unavailable credentials, retry behavior, and restoration from backup. Include scheduled work and operational procedures, not only interactive requests. Record test environment differences that prevent direct generalisation to production.

A synthetic example can illustrate the method. Suppose a rehearsal contains 10,000 source orders. The initial validation finds 9,970 records with matching required fields and 30 requiring investigation. After correcting a timestamp transformation, all 10,000 match the defined comparison. The chart reports 99.7% and 100% reconciliation coverage. It does not claim zero defects, production success, or a measured customer outcome; it covers only the declared fields and sample.

#Cut over through explicit gates

Create a timed runbook with decision owners, communication channels, prerequisite checks, commands or automation references, and verification evidence. Separate technical readiness from business authorization. The person coordinating the cutover should know who can pause it and what information supports that decision. Define a latest safe reversal point before irreversible data or contractual changes occur.

Reduce exposure gradually where the architecture permits it. A traffic percentage is only meaningful if routing, session affinity, caches, and background consumers are understood. Observe business outcomes alongside infrastructure health. A service can return successful HTTP responses while generating incorrect invoices or failing to publish required events. Keep the old environment available for the approved recovery period, with clear rules about whether it may receive writes.

#Rehearse rollback and forward recovery

For each change, identify what can be reversed directly, what requires restoring data, and what needs a compensating business action. Application binaries, schema changes, external messages, and user-visible decisions have different reversibility. Prefer compatible schema expansion before removing fields or old code paths. Test that the previous application version can still operate during the intended rollback window.

Do not call an untested backup a rollback plan. Restore into an isolated environment, verify the application can use the restored data, and measure the complete recovery sequence. Include key access, networking, deployment, reconciliation, and business validation. If a failure after cutover requires forward repair, document that explicitly and ensure the team has the tools and authority to perform it.

#Operate the new system deliberately

Assign ownership for patching, capacity, certificates, access reviews, alerting, backups, cost anomalies, and dependency upgrades. Establish dashboards around the service's critical journeys and failure modes. Alerts should identify an actionable condition, a responsible responder, and a useful first step. Retire obsolete checks only after confirming that their intended protection exists in the new operating model.

Observe the workload across relevant business cycles before declaring the transition complete. A quiet first week may omit billing, reporting, or peak demand. Track support effort and manual work introduced by the new platform. Modernisation can reduce one kind of toil while creating another, such as managing a new deployment abstraction or investigating unfamiliar managed-service limits. Include those costs in the review.

#Handover evidence and retire safely

Handover includes architecture decisions, infrastructure definitions, data contracts, test evidence, recovery procedures, dependency ownership, and known limitations. Ask an engineer who did not build the pilot to deploy a change, diagnose a controlled fault, and follow the recovery guide. Their ability to complete those tasks is stronger evidence of usable documentation than a large document bundle alone.

Retirement has its own checklist: confirm no required traffic or jobs remain, preserve approved records, remove credentials, terminate unnecessary resources, update inventories, and reconcile the final bill. Retention and licensing decisions belong to the appropriate organisational owners. Savings should be measured after overlap and transition costs are accounted for; deleting an invoice line in a spreadsheet does not demonstrate that the resource was safely removed.

#Use a decision worksheet and publish limits

The working worksheet records the workload, current constraint, alternatives, selected option, dependencies, data scope, acceptance tests, rollback boundary, owners, and open assumptions. For each proposed benefit, specify the baseline, formula, measurement window, and source. Separate recurring operating cost, one-time migration effort, and temporary dual-running cost. State the confidence range instead of presenting a single speculative payback date as certainty.

Review the worksheet at discovery, pilot acceptance, cutover, and operational handover. A newly discovered dependency or failed restore test can change the correct decision. The intended outcome is a defensible migration or retention choice with evidence that the chosen workload can be operated. The method does not promise that every application belongs in the cloud or that every cloud move reduces cost, latency, or organisational complexity.

#Confirm the commercial and exit assumptions

Review licensing, support eligibility, data-transfer charges, minimum commitments, and the cost of retaining a fallback environment. A technically compatible target may still be unsuitable when contract terms or staffing requirements are considered. Record the date and source of each commercial assumption and have the appropriate owner validate it before a purchase or commitment.

Also test an exit path at the scale relevant to the decision. Document how data can be exported, which formats preserve meaning, and which managed features would require application changes elsewhere. This does not require avoiding every provider-specific feature. It makes the benefit and the future switching work visible so the organisation can choose deliberately. An exit assessment should include restoration and application validation, rather than treating a successful file download as proof of portability.
