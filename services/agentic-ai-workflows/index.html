#What this service is designed to deliver

This is a proposed delivery methodology, illustrated with hypothetical organizations and synthetic measurements. It describes how an engineering team could build an assistant that completes a bounded workflow across tools. It is not a claim of completed customer work, a guarantee of savings or evidence from an undisclosed engagement. The five scenarios below demonstrate different applications of the method and the measurements needed before a real release.

The deliverable is an operating workflow with clear authority, evidence and recovery. A language model may interpret a request, select an appropriate tool or draft a proposal. Deterministic services still enforce identity, permissions, valid state transitions and resource limits. The model is not the source of authorization. The project succeeds when a user can complete the intended task reliably and an operator can explain every consequential effect.

#Discovery: choose a task with a finish line

Begin by observing the existing workflow with the people who perform and support it. Identify the trigger, required information, decision points, external systems and completion condition. Record ordinary cases and exceptions separately. A request such as "handle procurement" is too broad; "prepare a purchase request from an approved catalog for a named requester" supplies a boundary that can be implemented and tested.

Build a baseline using accepted tasks, including preparation, review, correction and recovery effort. Count abandoned attempts rather than removing them from the denominator. Ask which steps require judgment, which merely copy information and which can cause irreversible effects. This mapping often reveals that a conventional form or integration solves part of the problem more predictably than an agent.

Access discovery follows the actual data path. List user identities, workload identities, tool endpoints, document stores, model processors and telemetry destinations. Confirm the permitted data classes and retention rules for each. Use synthetic records while access is being reviewed. A development account with broad permissions is not an acceptable substitute for the restricted identity intended for production.

#Contracts: define evidence, proposals and effects

Write a contract for each tool: input schema, output schema, permissions, side effects, retry behavior, timeout and error categories. Separate read operations from proposal creation and execution. A proposal should identify the exact resource, requested change, evidence and expiry. Execution should reference that proposal and an authoritative approval or preauthorized policy, rather than accepting a model-generated statement that permission exists.

Bind approval to the actual effect. If a recipient, amount or resource changes, the previous approval should no longer authorize the changed operation. Include resource versions where concurrent updates matter. For repeatable mutations, define idempotency keys and request fingerprints. The service must atomically enforce the relationship between a recorded result and the corresponding effect; adding a key field to the tool description does not achieve this by itself.

Classify errors so the application can recover sensibly. Invalid input needs correction, authorization denial needs an appropriate access path, stale state needs refreshed evidence, and temporary unavailability may permit a bounded retry. A single catch-all instruction to "try again" can create duplicate effects, excessive load or a privilege escalation attempt during recovery.

#Architecture and data flow

A practical architecture has an authenticated entry point, a workflow state store, a model orchestration layer, scoped tool adapters, an authorization boundary and an event log. Retrieved or user-supplied content remains evidence rather than authority. The state store records proposed, approved, committed, failed and cancelled states so an interrupted conversation can resume without relying on a generated summary of what happened.

The model receives only the information needed for the current step. Context assembly preserves source identifiers and access labels, with explicit limits on history and tool results. Large result sets should support pagination or targeted follow-up instead of silently truncating critical records. Memory used across sessions needs provenance, expiry and deletion behavior, especially when a temporary instruction might otherwise become a permanent preference.

For HTTP MCP integrations, implement the applicable authorization flow and validate tokens for the intended resource. The current specification is a starting point, not permission to bypass application-level object authorization. Tool descriptions and annotations influence selection but do not establish trust. A server must independently verify which user or workload may act on which resource in the current state.

#Implementation in reviewable increments

First build a deterministic happy path using a fake tool service and a small synthetic fixture. This confirms schemas, state transitions and the completion contract without model variability. Add the model only where interpretation or synthesis is useful. Compare the result with the deterministic baseline so additional complexity has a measurable reason to exist.

Next implement exception paths: missing evidence, conflicting records, expired approval, version conflict, rate limiting and a timeout after commitment. Keep all effects in the fake environment until those paths can be inspected. Introduce production adapters behind narrow credentials and feature controls, with separate configuration for approved data boundaries. Review tool-name and description changes because they can alter model selection even when the backend API remains unchanged.

Set budgets across the entire workflow, not only individual calls. Bound attempts, elapsed time, tokens, tool invocations and monetary spend where applicable. Propagate cancellation to downstream services when supported. A request abandoned by the user should not continue an expensive exploratory loop indefinitely. For an ambiguous committed effect, surface the known state rather than fabricating success or failure.

#A synthetic delivery scorecard

Imagine a fixed rehearsal of 100 workflow requests. Eighty contain sufficient evidence; twenty are intentionally incomplete. The assistant produces valid proposals for 72 of the eighty complete requests and correctly requests clarification for 18 of the twenty incomplete requests. The chart shows 100 attempted requests, 80 complete inputs, 72 valid proposals and 18 appropriate clarifications. These measures overlap and must not be summed as independent groups.

Proposal success among complete inputs is 72/80, or 90%. Appropriate clarification among incomplete inputs is 18/20, also 90%. If the acceptance rule is a valid proposal or correct clarification, 72 + 18 = 90 of 100 cases meet it. This synthetic 90% is an illustration of the calculation, not a target suitable for every workflow or a measured model result.

A release decision also needs effect integrity, latency, user review effort and recovery evidence. A workflow can pass its language-quality rubric and still fail because it acts on the wrong tenant. Critical authorization tests are separate pass/fail requirements; they should not be averaged into a favorable overall score. Publish case definitions, versions, exclusions and reviewer disagreement alongside any quality percentage.

#Bounded testing and security review

Build tests at three layers. Tool-service tests call APIs directly with malformed, unauthorized and stale requests. Workflow tests exercise state transitions and interruption recovery. Model evaluations assess selection, evidence use, clarification and proposal quality on representative tasks. A model that behaves well cannot compensate for a tool service that accepts arbitrary object identifiers.

Defensive prompt-injection tests should use harmless markers and fake resources within an authorized test environment. Place conflicting instructions in retrieved documents and tool responses, then measure answer contamination, unauthorized proposals and committed effects separately. Include clean inputs to quantify the cost of overblocking. The objective is to verify boundaries, not to produce an impressive attack demonstration against unrelated systems.

Test retries after a server has committed but before the client receives the response. Confirm that the same operation returns the recorded result and a changed payload using the same key returns a conflict. Rehearse dependency outages, revoked access and a model that emits validly structured but semantically incorrect arguments. Keep the failure corpus versioned and expand it when real incidents reveal a new class.

#Acceptance and staged release

Agree on acceptance criteria before tuning. They should identify eligible tasks, required evidence, prohibited effects, latency bounds, maximum review burden and recovery behavior. The exact numerical thresholds belong to the workflow owner. A high-consequence action may require stricter controls than an internal draft, even if the model's average quality is identical.

Release first in shadow or proposal-only mode where appropriate, then to a defined cohort under explicit authority. Record the assignment and scope so pilot outcomes can be interpreted. Compare accepted-task effort with the baseline, including reviewer time. Do not infer causal productivity gains from a voluntary group of enthusiastic early adopters without acknowledging selection and learning effects.

A release package contains the configuration manifest, evaluation report, authorization map, runbook, cost model and known limitations. Approval should concern this concrete package. Changing the workflow's authority or data class requires review of the changed boundary, while routine operation within approved scope should remain usable without repeated unnecessary confirmation.

#Rollback, operation and handover

Rollback restores the compatible model, prompt, tool schema and workflow policy, not only a model identifier. It cannot undo an external effect automatically. Define compensating actions where possible and a manual recovery path where reversal is unsafe or unavailable. Preserve pending requests and their last authoritative state so users do not have to repeat a consequential action blindly.

Monitor service health, quality samples, tool failures, denied actions, retry volume and accepted-task cost. Keep random quality samples separate from complaint-driven traces. Limit sensitive content capture and control diagnostic access. Operators need correlation identifiers and authoritative events; a fluent assistant narrative is not sufficient evidence of what executed.

Handover includes a practical rehearsal in which the receiving team investigates a failed task, disables a capability, restores a compatible release and explains the audit trail. Supply tool contracts, fixture data, evaluation scripts, deployment instructions and an owner map. Record which assumptions remain untested and which integrations depend on vendor behavior. The service should be supportable without relying on the original implementer's memory.

#Decision worksheet and limitations

For each proposed workflow, complete: intended user, trigger, accepted outcome, data sources, permitted effects, authoritative approval, idempotency boundary, evaluation cohort, failure consequence, fallback, operator and retirement condition. Require evidence beside every important claim. A blank field identifies unfinished discovery rather than a detail to hide behind a confident architecture diagram.

Agentic workflows are a poor fit when the task has no inspectable success criterion, the required authority cannot be constrained, or errors cannot be detected before unacceptable harm. Some tasks are better handled by deterministic automation or a human decision supported by search. The methodology supports that conclusion as a successful discovery outcome. Expansion of autonomy should follow demonstrated capability and recoverability, not the availability of another tool.

#Design for the person supervising the workflow

The interface should show the proposed effect, the evidence used and the unresolved uncertainty together. A reviewer should not need to open several unrelated logs to discover that an amount changed or that a source is outdated. Use concrete status language such as draft prepared, approval expired or execution outcome unknown. Avoid a generic success banner when only one stage completed.

Measure whether users can recover from an error without repeating the whole task. Preserve safe draft work, explain which input needs correction and make cancellation visible. Accessibility, keyboard navigation and readable source links matter because oversight is only useful when people can actually inspect the decision. Include these interactions in the pilot acceptance exercise, alongside model quality and backend controls. An assistant that is technically bounded but difficult to supervise can still create unnecessary work and encourage users to approve proposals without adequate review.
