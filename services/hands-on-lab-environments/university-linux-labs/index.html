#Hypothetical need and access baseline

A fictional university computing programme has students using different laptop operating systems and processor architectures. The proposed lab teaches Linux service diagnosis with invented application data. It does not describe a delivered university engagement. Discovery records available memory, installation permissions, network restrictions and accessibility needs before deciding which students use local VMs and which need a supported remote environment.

#Environment and teaching design

The package includes a pinned guest image, cloud-init configuration, a small HTTP service and a deliberately broken configuration variant. Setup waits for initialization and verifies the expected starting state. The cloud-init readiness guidance supports that distinction: a running VM is not sufficient evidence that package installation and configuration have completed.

The learner's task begins only after the environment check passes. Students inspect service status, logs, listening sockets and a local request, then explain the fault before repairing it. The instructor supplies progressive hints and records whether the learner needed help with Linux concepts or with the environment itself. The capstone changes the configuration error so memorizing a restart command is insufficient.

#Synthetic capacity calculation

A hypothetical teaching session supports 12 local or remote guest environments, each configured with two GiB of memory. Guest allocation totals 24 GiB across the selected hosts. Four additional environments used for instructor demonstration and replacements add eight GiB, giving 32 GiB of guest allocation overall. The chart shows participant, support and combined allocation. It excludes host overhead and does not imply that all guests run on one 32-GiB machine.

The planning worksheet also records CPU, disk, download size and concurrency per host. A participant whose hardware cannot support the configuration receives the remote route before the assessment. Timing comparisons exclude provisioning incidents or report them separately rather than attributing them to student ability.

#Acceptance, cleanup and handover

Acceptance requires a fresh setup, correct diagnosis, a verified service response and an explanation of the evidence. The learner then resets the environment and demonstrates that the seeded fault returns reproducibly. Cleanup removes only the named lab guest and associated synthetic files, with explicit host-versus-guest command labels.

No production credentials or personal student records are placed inside the exercise. Access to remote environments expires after the planned retention period. Handover includes image and architecture support notes, readiness checks, fault variants and the rubric. A delayed exercise changes the service port and dependency configuration, assessing whether students can reapply the diagnostic method rather than repeat the exact original commands.
