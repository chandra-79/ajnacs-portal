#The proposed service and its limits

This methodology describes proposed security and identity work for AI applications. All scenarios and numerical examples are hypothetical and synthetic; they are not claims about protected customer engagements or measured production outcomes. The deliverable is an evidence-backed control design, tested implementation boundaries and an operating plan for the capabilities actually in scope.

The service treats an AI application as software with identities, data stores, dependencies and possible effects. Model robustness matters, but a prompt is not an authorization system. A model may misread a document or propose an inappropriate action; the surrounding services should still enforce who can access which resource and what operation is permitted. No finite evaluation can establish that prompt injection or misuse is universally impossible.

#Discovery: identify assets and authority

Inventory users, workload identities, model processors, retrieval stores, tool servers, artifact repositories and outbound destinations. For each, record the data it can read, the state it can change and the credentials it holds. Include less visible paths such as logs, caches, summaries, embeddings, rendered links and exported evaluation datasets. A read-only model interface can still expose confidential information through its answers.

Define the intended user task and the maximum authorized effect. A support assistant that drafts a response needs different permissions from one that changes account entitlements. Map the legitimate authority chain from authenticated user or approved automation policy to the backend operation. Do not accept a model-generated explanation as evidence that the user authorized a change.

Access discovery should use approved read-only inventories and test identities. Confirm the scope of any active validation before running it. Production credentials should not be copied into a broad development environment merely to make integration easier. Where access is unavailable, record the unverified assumption and use a synthetic fixture until the responsible owner supplies evidence.

#Threat model the complete data flow

Identify entry points for untrusted content: user text, retrieved documents, tool output, emails, web pages, file metadata and generated summaries. Then identify where that content could influence a privileged decision. The important boundary is not simply between two prompts; it is between evidence and authority to read, publish, modify or export.

Consider confidentiality, integrity and availability separately. An attacker may try to reveal a private passage, bias a summary, trigger a wrong mutation or exhaust a tool budget. A defense that blocks outbound network calls may reduce one exfiltration path while leaving misleading output or excessive computation possible. State the property each control is intended to protect and test it directly.

Record trust transitions when data is transformed. A low-privilege summarizer's output remains derived from untrusted input. A JSON schema constrains structure but does not make the values true or authoritative. Provenance and classification should survive extraction and summarization so downstream components do not accidentally promote a document's instruction into application policy.

#Identity and token design

Separate human identity, application identity and delegated authority. The backend should know whether a request represents a user, a scheduled workload or a service-to-service operation. Avoid a shared privileged account that makes every model-generated tool call appear equally authorized. Scope credentials to the resource and task, with lifecycle ownership and rotation procedures.

For OAuth-based integrations, follow the applicable protocol and current security guidance. Validate issuer, intended audience or resource, expiry and required scope according to the token format and deployment. Do not accept an ID token as an API access token merely because it is signed. Do not forward a token issued for one service to an unrelated upstream service as a shortcut around proper delegation.

HTTP MCP authorization provides a transport-level framework, while application services still need object and action checks. A valid token with a broad scope does not prove access to every tenant's record. Bind sessions and cached decisions to the relevant principal and authorization state. Token validity, user entitlement and resource ownership are separate questions that should remain visible in code and tests.

#Resource-level and tool-level controls

Define permissions as operations on resources under conditions. A draft tool can create an internal proposal without gaining permission to send it. A search tool should filter documents before they reach the model, and citation resolution should recheck access where permissions may change. The model should not be trusted to remove forbidden data after exposure.

For consequential actions, bind approval or preauthorized policy to the exact effect. Include resource identifier, relevant version, recipient or destination, amount where applicable and expiry. A changed proposal should require a new authorization decision. The service should enforce these bindings even when the tool is called directly without the model.

Idempotency and concurrency are part of integrity. A timeout after commitment can lead to a retry, so the service needs an atomic relationship between operation identity and effect. A stale read can lead to an incorrect update, so use version checks or an appropriate transaction. These are ordinary distributed-system controls with increased importance when a probabilistic planner chooses the call sequence.

#A synthetic permission-review ledger

Imagine an inventory of 300 workload grants. One hundred twenty have demonstrated current use and an accountable owner. Eighty appear unused in the observed window, sixty lack confirmed ownership and forty have insufficient telemetry. The chart shows those four exclusive review categories. The fully evidenced share is 120/300 = 40%.

The other 180 grants are not automatically safe to remove. An infrequent disaster-recovery job may be absent from a short observation period. Missing ownership may reflect an inventory defect, while missing telemetry prevents a sound usage conclusion. The review should gather evidence, identify dependencies and stage any reduction with rollback. This synthetic ledger illustrates prioritization rather than a claim that sixty percent of permissions are unnecessary.

If owners and usage evidence are established for fifty additional grants, evidenced coverage becomes 170/300, approximately 56.7%. That is an inventory-quality improvement, not proof of reduced breach probability. Publish the observation window, classification rules and unresolved cases so the metric cannot be improved merely by hiding difficult permissions.

#Data minimization, egress and artifact integrity

Minimize the information supplied to the model and tools for the task. Shared caches must respect authorization scope and invalidation when access changes. Deleting an original document may require changes to derived summaries, embeddings and retained examples. The implementation should identify those stores and their retention owners before accumulating sensitive material.

Constrain outbound destinations and actions according to the integration. A domain allowlist is useful but may still permit attacker-controlled resources within an approved service. Review paths, recipients, methods and data classes where necessary. Prevent automatic rendering of arbitrary remote content from becoming an unreviewed outbound channel, and test the actual client behavior rather than assuming generated text is inert.

Model artifacts, adapters, prompt configurations and tool packages are software supply-chain inputs. Verify provenance and integrity appropriate to their source, restrict who can publish releases and keep development experiments separate from production artifacts. An artifact repository should not expose training data or credentials through convenience downloads. Record what was reviewed and what remains dependent on vendor assurance.

#Implementation in bounded stages

Begin with a fake application and synthetic records. Implement authorization checks independently of the model, then call the tools directly with valid, invalid and cross-resource requests. This establishes the service boundary before adding the complexity of model-driven selection. Keep the fixture small enough that expected effects can be inspected manually.

Next integrate the model with restricted tools and explicit state. Add structured error categories, attempt budgets and cancellation. A permission denial should not cause the agent to search for a more privileged identity or an unapproved destination. Recovery should preserve the authorized scope rather than widening it in pursuit of task completion.

Introduce real integrations only after their contracts and access paths are understood. Use a limited cohort or proposal-only mode where appropriate, with a tested disable path. Changes to tool authority, data classification or processor should trigger review of the changed boundary. Routine authorized use should remain usable; security controls that require unnecessary repeated approval can encourage people to work around them.

#Defensive evaluation and acceptance

The test plan should cover authentication, object authorization, session isolation, stale permissions, expired approvals, duplicate calls and rate limits. Add benign prompt-injection fixtures that attempt to introduce an unrelated marker or an unauthorized fake action through documents and tool output. Run only within the authorized test environment and use no real secrets or external exfiltration destination.

Measure attempted violations and committed effects separately. A model may propose a forbidden action that the backend correctly rejects. Conversely, a model that behaves well in the evaluation does not prove the backend would reject a direct unauthorized call. Report legitimate task completion as well, because denying every request is not a useful security design.

Acceptance should identify critical invariants and residual risk. No tested cross-tenant disclosure, correct token-resource binding and exact approval enforcement can be concrete requirements. The test corpus, identities, policy version and limitations should accompany the result. Avoid a universal "secure AI" score that averages a serious authorization failure into many successful ordinary responses.

#Incident response and rollback

Prepare a capability-level disable mechanism so an affected write tool can be stopped while safe read functions remain available where appropriate. Preserve authoritative events, configuration versions and relevant source identifiers for investigation. Limit sensitive content capture to approved purposes and access roles. The assistant's narrative is useful context but not the source of truth for committed effects.

Rollback restores compatible policy, tool schema, prompt and model configuration. It cannot automatically reverse every external effect. Define compensation and manual reconciliation for operations that can commit before an error is observed. Revoke exposed credentials through the identity system and test that cached sessions or delegated access do not continue beyond the intended revocation behavior.

After an incident, distinguish the failed control from the triggering text. Strengthening a prompt may reduce recurrence while leaving the authorization defect intact. Add a regression case at the layer that should enforce the property, review related paths and document the residual limitation. A useful incident process improves the boundary rather than merely adding a longer warning to the model.

#Handover and practical worksheet

Handover should include identity and resource maps, token-validation assumptions, policy definitions, tool contracts, test fixtures, deployment controls, incident runbooks and evidence-retention decisions. The receiving team should demonstrate revocation, capability disablement, denied cross-resource access and recovery from an ambiguous committed operation. This exercise tests whether controls can actually be operated.

For each capability, complete a worksheet: authenticated principal, delegated authority, allowed resources, permitted actions, data classification, approval source, expiry, idempotency boundary, egress destination, audit event, owner and disable procedure. Attach the relevant test evidence and mark unverified dependencies. The worksheet should be concise enough to update when a new tool is added.

#Limits and tradeoffs

Stricter permissions can increase integration work and require better error handling. Detailed telemetry can improve investigation while increasing sensitive-data exposure. Human review can catch some mistakes but fails when the interface hides effects or reviewers lack time and authority. The design should make these tradeoffs explicit and test usability alongside enforcement.

Security assurance remains scoped to the application, policy and evidence reviewed. New tools, new data sources and changed identities can alter the threat model. The service therefore aims for a maintainable control system with clear responsibility and repeatable validation, rather than a claim that a model has become impossible to deceive. That distinction makes the resulting application more dependable and its limitations more honest.
