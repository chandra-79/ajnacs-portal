Build replayable sensor data for maintenance models

Hypothetical ingestion and replay design that preserves sensor timing, quality flags and maintenance-label provenance.

#Proposed problem and operating scope

A hypothetical factory has equipment sensors and maintenance records stored in separate systems. Analysts can train a failure-risk model, but cannot reliably reconstruct the inputs used for a past prediction. The proposed work would build a replayable data path and a validated scoring release. It would not authorize automatic machine shutdown or replace the plant's maintenance safety procedures. All measurements below are synthetic.

Discovery would map sensor clocks, sampling rates, device resets, missing intervals and maintenance-label creation. A repair recorded after a failure must not leak into features used before that failure. The team would also identify which sensor values are diagnostic quality flags rather than physical measurements. Treating a missing signal as a real zero could create a false operating condition.

#Architecture and implementation

The ingestion layer would preserve raw event identifiers and timestamps, then validate units and ranges. A transformation stage would produce versioned windows with explicit missingness and clock-quality indicators. Training datasets would join only information available at the prediction cutoff. The scoring artifact would include the preprocessing version and a documented fallback when sensor coverage is inadequate.

Implementation would use synthetic traces with a device reset, a duplicated batch and a delayed maintenance record. Replay would be tested from a recorded checkpoint, with output identities preventing duplicate scoring records. A bounded failure rehearsal would stop a worker mid-window and confirm that resumed processing reconstructs the same accepted window values. The ML Test Score provides useful background for these data and infrastructure checks.

#Synthetic replay arithmetic

Assume a rehearsal has 600 expected sensor windows. Five hundred forty meet the coverage rule, forty contain insufficient samples and twenty fail clock validation. The chart shows the three exclusive outcomes. Eligible-window coverage is 540/600 = 90%. The sixty ineligible windows should retain their reason codes instead of disappearing from the training population.

If a new buffering policy recovers twenty of the forty sparse windows, eligible coverage becomes 560/600, approximately 93.3%. That does not prove a lower equipment-failure rate or improved model accuracy. It demonstrates a specific data-availability change whose downstream effect still requires separate evaluation.

#Acceptance and handover

Acceptance would require reproducible window values, no future maintenance information in historical features, explicit quality flags and successful restart recovery. Model quality would be reviewed on a time-appropriate holdout with equipment grouping where needed. The proposed system would expose risk estimates to qualified maintenance staff, not issue unreviewed safety actions.

Rollback would restore the previous transformation and model pair, while preserving raw data needed for replay. Handover would include clock assumptions, source ownership, replay capacity, missing-data runbooks and a demonstration of tracing one prediction to its sensor windows. The principal limitation is label quality: a technically sound pipeline cannot turn incomplete maintenance records into definitive failure ground truth.
