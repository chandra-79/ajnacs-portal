Hypothetical · Insurance software

Refactor a pricing rule with explicit behavioural evidence

A hypothetical maintenance workshop preserves declared rules while separating data access from calculation.

#Hypothetical need and baseline

A fictional insurance-software team maintains a large function combining input parsing, database reads and a simplified pricing calculation. The lab uses invented products and rates with no actuarial or commercial validity. It teaches refactoring and verification, not insurance advice or a real customer's pricing model. The baseline asks learners to trace one input through the function and identify which behaviours are specified, accidental or unknown.

#Technical approach

The instructor supplies a small decision table and a set of historical-style synthetic fixtures. Participants first capture the agreed existing behaviour, including rounding and invalid inputs. They then separate pure calculation from data retrieval and response formatting without changing the declared result. An interface is introduced only where it clarifies responsibility or enables a meaningful test seam.

The exercise deliberately includes one surprising legacy behaviour. Learners must seek a domain decision rather than quietly “clean it up” during refactoring. The change record distinguishes preserved behaviour from an approved correction. Decimal arithmetic is used for the invented monetary calculation, with an explicit rounding stage; the Python decimal documentation provides a reference implementation option rather than a mandated language.

#Synthetic worksheet and chart

The constructed suite contains 30 rule examples: 18 ordinary cases, eight boundary cases and four invalid-input cases. The chart shows that distribution. These are designed examples, not measured production frequencies or evidence that 30 tests establish complete correctness. Each fixture includes the business explanation and expected result so the suite can be reviewed without reading the implementation line by line.

Participants add a controlled mutation, such as applying a discount before rather than after a specified threshold comparison, and verify that the relevant test fails. A suite that stays green after the seeded defect needs improvement. Coverage is reported only as supporting information; executing a line does not prove that the important decision was checked.

#Acceptance, release and handover

Acceptance requires unchanged results for all preserved behaviours, explicit evidence for any approved correction, no hidden database access in the pure calculation and a reviewable diff. The learner explains why the new boundary improves the actual maintenance task and what complexity it adds. A smaller function count is not a success criterion by itself.

The release exercise uses a compatible artifact and a synthetic comparison report before switching the lab's active version. Rollback restores the previous artifact because the exercise intentionally avoids persistent schema changes. Cleanup removes fixtures and temporary databases after exporting the evidence. Handover includes the decision table, labelled test corpus and rationale for the boundary. A delayed task adds a new rule with a different ordering constraint, testing whether the team can extend the model without assuming every future rule fits the same abstraction.
