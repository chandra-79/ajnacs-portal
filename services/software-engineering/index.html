#Programme purpose and scope

This proposed software-engineering enablement programme develops the ability to change an existing service safely, explain the design and verify the resulting behaviour. The focus is delivery competence: understanding requirements, reading unfamiliar code, shaping interfaces, testing meaningful risks, reviewing changes and operating the result. It is adapted to the organisation's languages and framework versions rather than presenting one stack as a universal answer. All cases and numerical examples on this page are hypothetical teaching scenarios, not accounts of customer work.

Discovery starts with a small sample of actual engineering responsibilities, described without exposing confidential code or data. Identify whether learners mainly build APIs, maintain business rules, operate data workflows or support user interfaces. Record the expected level of independence and the constraints of the team's delivery process. A programme for experienced maintainers adopting a new framework should not duplicate a beginner course, while a new engineer should not be assessed on unstated infrastructure prerequisites.

#Baseline through a realistic change

The baseline task uses a small synthetic repository with a readable specification and a seeded defect. Participants locate the relevant code, describe the existing behaviour, propose a bounded change and demonstrate it with evidence. The assessor records where help was needed: language syntax, domain reasoning, test design, tooling or diagnosis. This produces a learning-needs map that can guide preparation and pairing without turning the exercise into a public leaderboard.

Assess explanation separately from completion speed. A fast change that bypasses authorization or ignores an error path is not equivalent to a correct change. Allow documentation and ordinary development tools during the assessment, because the goal is sound engineering rather than memorized APIs. If an assistant or code generator is used, record its role and require the participant to explain and verify the resulting code. Tool assistance does not transfer accountability for correctness.

#Establish an inspectable reference application

The laboratory application contains a small API, a relational data model, one asynchronous operation and a minimal user-facing workflow. Its domain is deliberately understandable, such as equipment booking or order tracking. Fixtures are entirely invented and small enough to inspect manually. The repository includes versioned dependencies, setup instructions, a supported test command and a clear distinction between required configuration and optional integrations.

Keep the architecture modest. A module boundary, interface or repository abstraction is introduced when it supports a real responsibility or test seam, not to demonstrate every design pattern. Participants trace one operation from request validation through business rules to persistence and response. They identify where an invariant belongs and which failure can cross each boundary. This makes later design discussions concrete instead of relying on diagrams disconnected from executable behaviour.

#Requirements become examples and invariants

Translate a feature request into observable examples, boundary cases and rules that must always hold within the declared scope. For a booking service, two accepted reservations must not claim the same exclusive resource and interval. For an order operation, a retry must not create another business order when the contract promises idempotency. The team writes these rules before choosing a framework annotation or database query.

Separate missing information from implementation freedom. The instructor supplies business decisions that the exercise genuinely requires, while learners make routine technical choices and record their rationale. An acceptance worksheet contains the actor, precondition, action, expected result, failure result and evidence. Include accessibility and error recovery when a user interface is involved. A happy-path screenshot is not enough to establish that a person can recover from invalid input or an expired session.

#Design interfaces with compatibility and authorization

API exercises define request and response shapes, status semantics, pagination behaviour and error identifiers. OpenAPI can describe the interface, but runtime validation and executing consumer tests are still required. Participants distinguish a machine-readable contract from a promise that every generated client handles every edge case correctly. They test absent optional fields, unknown values and malformed input with deliberate examples.

Authorization is checked against the authenticated actor and the resource, including alternate lookup paths and list endpoints. A client-supplied tenant identifier is not trusted simply because it has the right type. The lab includes two fictional tenants and attempts to cross their boundary. Learners should be able to explain why validation, authentication and authorization solve different problems and where each is enforced in the application.

#Make data correctness visible under concurrency

A transaction is selected to protect a specific invariant, with the database isolation level and conflict behaviour understood. Participants run two controlled concurrent operations against the same synthetic resource. They observe whether constraints, version checks, locks or serializable execution provide the intended result. An ORM session or a framework transaction decorator is not accepted as proof that every race has been resolved.

The data module also covers schema evolution. Learners add a field through a staged change that supports the intended old and new application combinations. They identify which changes can be reversed safely and which require forward repair or restoration. Test fixtures include existing rows, empty values and a failed migration attempt. The handover must preserve the data assumptions; a rollback command without compatibility conditions is incomplete.

#Test risks at the appropriate boundary

Use fast unit tests for isolated business decisions, integration tests for database and adapter semantics, and a small number of end-to-end tests for critical user journeys. The exact distribution depends on the application. A high test count or coverage percentage is not the goal; the useful question is which important failure each test would detect. Participants deliberately introduce a defect and check that the relevant test fails for the intended reason.

Fixtures should reveal their scope and cleanup behaviour. Shared mutable fixtures can make tests pass only in a particular order, while excessive mocking can verify an imagined dependency rather than the real interface. The programme uses the selected framework's official fixture guidance and asks learners to run a test alone, in a suite and after a failed setup. Tests that require secrets or external paid services are isolated and explicitly controlled.

#Teach debugging and performance as experiments

Debugging starts with a reproducible symptom, a hypothesis and the smallest useful observation. Learners inspect the actual exception, query, request or state transition before changing code. They retain the failing fixture and add a regression check after the repair. The assessment rewards narrowing the cause and preserving evidence, not simply restarting the service until the symptom disappears.

Performance work uses a declared workload and correctness checks. A synthetic request might spend 120 milliseconds waiting for a database, 80 transforming data and 40 serializing a response, totalling 240 milliseconds in a simplified sequential model. Those inputs can guide a discussion, but actual profiling must account for concurrency, measurement overhead and overlapping work. Participants must distinguish fewer queries from faster response time and a faster successful subset from better overall completion.

#Review changes as maintainable artifacts

Each change is submitted as a small reviewable diff with a description of the problem, resulting behaviour, verification and known limits. Reviewers inspect naming, responsibility boundaries, error handling, data access and test meaning. They also check whether a clever abstraction is justified by current use cases. The exercise includes a tempting generic helper whose callers have different semantics, encouraging a reasoned choice between reuse and explicit duplication.

Pairs rotate author and reviewer roles. A review comment should explain the consequence of a problem and offer a testable direction, rather than enforce personal style without context. The author responds with evidence or a revised decision. Preserve one design record for a material tradeoff, including alternatives and conditions that would cause the team to revisit it. This teaches how to communicate technical judgement as part of delivery.

#Build and release with controlled permissions

The pipeline installs declared dependencies, runs the relevant checks, creates an identifiable artifact and records the source revision. It separates untrusted contribution checks from jobs that can access deployment credentials. GitHub Actions or another platform's security model must be reviewed for the actual workflow; a green CI badge does not establish that secrets cannot leak or that third-party build steps are trustworthy.

Use least-privilege tokens, reviewed dependencies and a clear artifact promotion path. Learners inspect a deliberately unsafe workflow that combines untrusted code with powerful credentials, then explain a safer boundary. Deployment exercises use only the lab environment. The release record identifies the artifact, configuration, migration state and verification result, making it possible to determine what actually ran rather than relying on a mutable branch name.

#Operability and rollback belong in the feature

The application provides useful structured diagnostics without logging secrets or entire personal records. A business-operation identifier helps connect requests, background work and persistent outcomes. Health checks represent the application's actual readiness and failure behaviour. Participants create a support note that explains common failure states and the evidence needed to distinguish them.

Rollback is rehearsed for a compatible application change, then contrasted with an incompatible data change. The learner names the previous artifact, stop condition, data assumptions and verification steps. External effects such as messages or provider calls may require reconciliation or compensation rather than reversal. A correct answer can be that rollback is unsafe and a bounded forward repair is required, provided the reasoning and recovery plan are explicit.

#Capstone design and assessment evidence

The capstone is a fresh feature with an unseen defect and a small operational complication. It requires a contract change, a data rule, meaningful tests, a reviewed implementation and a release or recovery demonstration. Instructors may answer business questions but record technical hints. The final assessment includes an explanation to another engineer who did not write the code, testing whether the solution is understandable and transferable.

The methodology figure shows a hypothetical 24-check acceptance design: nine correctness checks, six security checks, five operability checks and four migration checks. These are planned evidence items, not observed defect counts or a universal test allocation. Every required check has a defined expected result. A participant cannot compensate for a failed authorization requirement by passing more formatting checks. Critical acceptance conditions remain explicit rather than disappearing inside an average score.

#Resource budget, cleanup and handover

Estimate repository setup, environment runtime, database storage and any external test-service usage before delivery. Local execution may reduce cloud runtime but still requires sufficient participant hardware and support. A shared remote environment changes isolation and scheduling assumptions. Choose the option that supports the learning objective and accessibility needs, and keep an inventory of owner, purpose and expiry for provisioned resources.

Cleanup removes test credentials, deployments, temporary data and paid integrations after preserving non-sensitive assessment artifacts. The handover includes the repository, dependency manifest, fixture generators, test strategy, architecture notes, review examples, runbooks and capstone rubric. An internal maintainer rebuilds the project from a clean environment. Any missing undocumented setup step is corrected before the material is considered reusable.

#Measure transfer without inventing a productivity claim

A delayed exercise asks participants to change a related but unfamiliar part of the application. Measure independent completion, correctness, quality of diagnosis and the ability to explain tradeoffs. Compare tasks only when their difficulty and scoring are sufficiently similar, and report the small cohort's limitations. Attendance, confidence surveys and demonstrated competence are different outcomes and should remain separate.

If the organisation later measures delivery or incident metrics, preserve baseline definitions and competing explanations such as staffing, tooling and workload changes. This programme does not promise a percentage improvement from training alone. The proposed deliverable is a reproducible capability: engineers who can make a bounded change, test its important risks, communicate it clearly and hand over evidence that another maintainer can use.
